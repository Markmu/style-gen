## Blocker 清单

### B1（阻塞）：`normalizeRuleArray` 规范化顺序与规格相反，"仅空白差异"可被误判为实质变更

- 位置：`src/lib/style-memory-rules.ts:9-14`
- 规格口径：架构 §6.4"逐元素 trim → 排序 → 逗号连接的规范化串比较"；本计划实现规格 §4"逐元素 trim，过滤空串，按字典序排序"。
- 实现：`[...rules].sort(原始串字典序).map(trim).filter(非空)`——先按**原始串**排序、后 trim/过滤（源码注释自述"按原始串字典序排序 → 逐元素 trim → 过滤空串"，与计划规格顺序相反）。
- 实证（node 复算 + 对照规格实现）：

  | 输入（previous → next） | 实现 | 规格语义 |
  | --- | --- | --- |
  | `[" soft light", "golden hour"] → ["soft light", "golden hour"]`（纯空白清理，元素顺序未动） | **true（回退）** | false（不回退） |
  | `[" b", "a"] → ["a", "b"]` | **true（回退）** | false（不回退） |
  | `[" rule a ", "rule b"] → ["rule a", "rule b"]`（后置空白，不翻转排序） | false | false |

  机理：空格（0x20）小于所有字母，带前导空格的元素在原始串排序中会提前，trim 后相对顺序翻转，导致归一化序列元素错位比较失败。已勾选验收标准"仅改序/trim 差异 → 不回退"对含前导空格的多元素输入不成立；现有 13 个用例（含 `" rule a "` 后置空白）恰好落在不翻转顺序的输入上，未覆盖该分支。
- 影响评估：错误方向单一且保守——只会把语义相等的集合误判为"实质变更"从而多回退 `pending_verification`，不会反向保留虚假 `user_verified`，状态诚实性不变式（§3.3）未被破坏，plan-05 复用同一实现故前后端口径仍一致；但作为"唯一实现"的核心判定算法，其行为与三处文档（架构 §6.4、计划实现规格 §4、函数自身 docstring 声明的语义）不符，属实现规格显式要求内的正确性错误，判定 blocker。
- 修复建议（交回 implementer）：调整为先 `map(trim)` → `filter(非空)` → 再 `sort`（一行顺序调换），并补充用例：前导空白 + 多元素（纯清理不回退）、前导空白 + 改序（不回退）。同步核对 `style-memory-rules.test.ts` 与 repository 回退用例不受影响（现有用例在两种顺序下结果一致，预期可直接保持绿）。
