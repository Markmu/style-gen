## 二、重点审查结论（对照架构 §7.3/§6.4/§8.2/§8.3/§8.5）

1. **信任边界（ADR-1）**：POST 在 `validateCreateBody` 首行拒绝 `verificationStatus`（→ 400 INVALID_REQUEST）；PUT 在解析请求体后显式拒绝并返回专用错误文案；representative-result 天然无该字段。5 个路由对 `verificationStatus` 仅做拒绝（POST/PUT）与只读消费（列表筛选透传、日志、回退判定），无任何直接写；状态变化只经 plan-01 repository 的 `createTemplate`（派生）/`setRepresentativeResult`（原子置 user_verified）/`updateTemplate`（ruleSetsChanged 回退）三个写点。
2. **representative-result 相关集与 action 判定**：路由校验 `task.sourceTemplateId === id || task.id === memory.sourceGenerationTaskId`，与 plan-01 候选查询 SQL（`source_template_id = templateId OR id = (SELECT source_generation_task_id …)`）完全同口径；任务归属/completed/resultAssetId 三重前置校验齐备且失败不写入（测试断言 `setRepresentativeResult` 未被调用）。`action` 以更新前 `memory.representativeGenerationTaskId` 判定 set/replace（记录在原子更新前读取），正确。
3. **限流（§8.3）**：`RATE_LIMIT_CONFIGS.templateWrite = { windowMs: 3600000, maxRequests: 30 }`；旧 `route.ts` 本地 `rateLimitStore/checkRateLimit` 已删除；共享 `checkRateLimit(userId, "templateWrite", …)` 接入全部 5 个写端点（POST/PUT/DELETE/duplicate/representative-result），identifier 一律取 session userId；GET 列表与 representative-candidates 无限流调用；429 响应 `{ error, code: "RATE_LIMITED", retryable: true }` 口径一致。测试对 POST（含 identifier+config 断言）与 representative-result 两端点做了深断言，符合验收标准"单端点抽查即可"的口径；PUT/DELETE/duplicate 接入由代码审查确认。
4. **409 统一（§8.2）**：全仓（src + e2e）搜索 `code: "CONFLICT"` 无残留，仅存 `TEMPLATE_NAME_CONFLICT`（POST 既有 + PUT 统一后）。
5. **输入上限校验（§8.3）**：POST `description ≤500`、`retainedRules/negativeConstraints ≤12 条 × ≤200 字符`、`styleTokens/enhancementHints ≤16 条 × ≤80 字符`（`validateBoundedStringArray` 参数化实现）；`representativeGenerationTaskId` 强制等于 `sourceGenerationTaskId`，且复用既有来源迭代校验（归属/completed/resultAssetId）；PUT 规则数组同规格校验、`variables` 沿用既有 `validateVariables`；非法输入错误信息为固定文案，不回显规则全文（符合"日志/错误不输出规则全文"）。测试覆盖 9 组越界数据行。
6. **日志事件（§8.5）**：`template_created` 增记 `verificationStatus` + `retainedRuleCount`/`negativeConstraintCount` + `representativePresent`；`template_updated` 增记 `verificationStatus` + `rulesChanged`；回退时记 `template_verification_reset { templateId, trigger: "rules"|"constraints" }`（trigger 复用 `ruleSetsChanged` 判定，仅 constraints 变更时报 "constraints"，正确）；新端点记 `representative_result_set { templateId, generationTaskId, action: "set"|"replace" }`；`template_detail_queried` 增记 `verificationStatus`。`style_memory_reused` 属 plan-07 预检范围，本功能不涉及（正确未实现）。
7. **实现者三项自主决策评估**：
   - **cursor 格式校验 400**：合理。GET 列表对非法 cursor 400 是既有行为（旧代码即对非 ISO 日期 400），本次仅将格式从单 ISO 日期迁到 `(ISO date)::id` 双键编码以对齐 plan-01 repository 契约；representative-candidates 采用同一 `parseCursor` 严格校验，两端点一致。无需回写计划（计划已规定游标为 `(sortTs,id)` 编码串）。
   - **PUT 空 description 清空**：合理。`UpdateStyleMemoryRequest.description?: string | null`（plan-01 类型契约）显式支持 null；`null` 与 trim 空串均映射为清空，与 repository `undefined=不改 / null=清空` 语义闭合；POST 侧"空串等同未提供"最终落库同为 null，两侧无矛盾。类型契约已承载该语义，无需回写计划。
   - **representative-result 并发删除 404**：合理且在计划内——边界场景表已明文"Memory 已被并发删除（PUT/representative）→ 404，无部分写入"；`setRepresentativeResult` 单条 UPDATE，0 行抛错 → 404，无部分写入。
8. **red 测试文件未被修改**：全部工作区改动未提交，无法用 git 快照比对 red 时点，故采用内容级核对——5 个测试文件的用例清单、计数（35/11/11/5/14 = 76）与 red 证据「测试清单」逐条吻合；red 失败摘要中的全部关键断言（createTemplate 收到扩展字段、representative≠source 400、verificationStatus 400、9 组越界 400、status 白名单 400 与透传、findStyleMemoryDetail 接入、PUT 五字段、`TEMPLATE_NAME_CONFLICT`、共享 `checkRateLimit("user-1","templateWrite",…)`、`RATE_LIMIT_CONFIGS.templateWrite` 形状）在当前文件中全部原样存在，未发现删例、跳过（skip/only）或断言放宽；76−60=16 的差值与 green 证据"两个 red 阶段加载失败套件恢复执行"的解释一致。

## 五、建议项（非阻塞）

1. **`无 session 取 x-forwarded-for` 回退分支未实现**（规格 §1 字面 vs 实现）：5 个写端点均先 `requireAuth`（401 短路）再限流，"无 session" 场景在限流调用点不可达，IP 回退成为死规格。边界场景表"未登录 → 401"的口径优先且已满足，判定为合理简化而非偏差；建议后续维护时在 plan 文件或 rate-limit 注释中标注该分支有意省略。
2. **PUT 与 representative-result 的内层 catch 会把 `updateTemplate`/`setRepresentativeResult` 抛出的任意错误映射为 404**：若 DB 在前置 `findById` 成功后、写语句执行时故障，会被误报 404 而非 503。与既有 DELETE 的 try/catch → 404 模式一致（沿用既有惯例），且窗口极小，不构成 blocker；建议后续用可识别的错误类型（而非 message 字符串）区分 not-found 与 DB 故障。
3. **`enforceTemplateWriteRateLimit`/`requireAuth`/`log`/`parseCursor` 在 4 个路由文件重复**：计划"允许修改的额外文件: 无"约束下的合规做法；若后续出现第 6 个写端点，建议申请抽公共 helper。
4. **limit 超上限的口径两端不一致**：列表 `limit>50 → 400`（沿用既有契约），candidates `limit>50 → 50 截断`（对齐 plan-01 repository `Math.min`）。两者各自有据（列表沿用既有、candidates 对齐 repository），非契约错误；建议 plan-04/05 前端消费时统一按 ≤50 传参。
5. **`generationTaskId`/`sourceGenerationTaskId` 仅校验"≤26 字符"**（未强制恰为 26 位 ULID）：短 id 会通过格式校验后在归属查询处被拒（400/404），无安全影响，与既有 `validateSourceAssetId` 惯例一致，仅记录。
