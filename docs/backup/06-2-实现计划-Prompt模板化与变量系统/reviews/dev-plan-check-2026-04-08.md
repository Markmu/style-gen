**建议**：
- 在 **T01** 的验证命令或预期结果中补充：「extractVariables 对合法 `{{var}}` 格式的准确率目标 >= 99%（通过边界测试用例覆盖）」
- 在 **T01** 的预期结果中补充 replaceVariables 正确率 >= 99% 的说明
- 在 **T04** 的预期结果中补充端到端闭环走通率 100% 的验收标准
- 保存成功率和加载耗时属于运行时指标，建议在 **T04** 的手动验证步骤中添加性能观察点说明（如："观察保存操作响应时间应在 200ms 内、加载操作在 500ms 内"）

### 2. Rate Limit（30 次/小时/IP）未在任何任务中实现 [严重程度: 中]

**架构文档要求**（8.3 安全策略）：模板创建 Rate Limit 为 **30 次/小时/IP**。

**开发计划现状**：T02 的实现规格中包含认证、校验、错误处理、日志，但**完全没有提及 Rate Limit**。T02 的文件清单和 Task 列表中无任何限流相关条目。README 的架构约束中也未列出此项。

**建议**：在 **T02** 中新增一个 Task 或在现有 Task 中补充 Rate Limit 实现规格：
- 可采用简单的内存计数器或中间件方案（首版并发 < 20，无需 Redis）
- 在 POST /api/templates handler 入口处增加 IP 级别的频率检查
- 超限时返回 429 `{ error: "请求过于频繁", code: "RATE_LIMITED", retryable: true }`

### 5. L1/L2 降级行为未在后端任务中显式编码 [严重程度: 低]

**架构文档要求**（8.2 降级策略）：

| 级别 | 触发条件 | 系统行为 |
|---|---|---|
| L1 | 数据库写入延迟 | 请求超时后前端提示重试 |
| L2 | 数据库不可用 | 返回 503，模板 CRUD 不可用但主链路不受影响 |

**开发计划现状**：
- T02 的 catch-all 返回 500（而非 503），且 `retryable: true` 已隐式支持重试语义
- 但没有区分"数据库超时"和"其他内部错误"的差异化处理
- 前端侧（T03/T04）的错误处理是通用的 try-catch，未针对 503 做特殊 UI 反馈

**建议**：当前 T02 的通用 500 兜底对于首版来说可以接受（Next.js 框架层面可能已有超时处理）。如果希望严格对齐架构文档，可在 **T02** 的 catch 块中增加错误类型判断：检测到数据库连接/超时类错误时返回 503 而非 500。优先级低，因为：
1. 首版无专用数据库超时配置
2. 500 + retryable:true 对用户而言体验差异不大

**无阻塞性缺失**：所有缺失项均不影响 P0 功能的正确实现，可在开发过程中或后续迭代中补充。
