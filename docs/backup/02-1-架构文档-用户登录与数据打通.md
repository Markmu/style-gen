# 架构设计文档：用户登录与数据打通

_本文件只保留当前版本真正影响实现的架构决策、边界和契约；DDL、目录树、环境变量、实施故事等内容默认不放入正文。_

## 1. 系统摘要

为已完成的创作闭环建立用户身份基础设施。通过 Google OAuth 实现一键登录，所有业务数据（资产、分析任务、生成任务）关联到用户，实现数据跨会话持久化和用户级隔离。

核心闭环：**OAuth → Identify → Isolate**（认证 → 识别 → 隔离）

首版定位：最小可用的用户身份基础设施。不做复杂用户管理，只做身份识别和数据关联。

## 2. 范围、非目标与成功标准

### 2.1 P0 范围

- Google OAuth 登录（仅 Google，不支持其他方式）
- 用户记录自动创建/更新（首次登录创建，再次登录更新）
- 页面访问控制（首页开放，工作区需登录，未登录重定向首页）
- API 认证验证（所有业务接口需确认用户身份）
- 数据关联（资产、分析任务、生成任务均关联到用户）
- 数据隔离（用户只能查询和操作自己的数据）
- 顶部导航栏用户信息下拉框（头像 + 名称 + 邮箱 + 退出登录）
- 退出登录（清除会话，恢复未登录状态）
- 会话持久化（7 天内免重复登录）

### 2.2 P1 预留

- 历史记录列表页
- 登录失败重试和错误提示
- 会话过期自动跳转登录

### 2.3 明确不做

- 用户资料编辑页、多登录方式（GitHub、邮箱等）
- 团队组织、角色权限、配额付费
- 忘记密码/重置密码、更换邮箱/绑定手机
- 账号注销/数据导出、多设备登录管理
- 现有匿名数据迁移

### 2.4 成功标准

| 指标 | 首版目标 |
| --- | --- |
| 登录成功率 | >= 99% |
| 登录到可操作耗时 | <= 5 秒（中位时间） |
| 数据关联准确率 | 100% |
| 数据隔离准确率 | 100% |
| 会话恢复率 | >= 95% |
| CTA 登录转化率 | >= 80% |

## 3. 关键架构决策（ADR）

### ADR-7：认证方案选择 Auth.js (NextAuth v5)

- **选择**：使用 Auth.js v5 集成 Google OAuth，采用 JWT 会话策略（httpOnly cookie）
- **理由**：Auth.js 是 Next.js 生态最成熟的认证方案，内置 Google Provider，自动处理 OAuth 回调、JWT 签发/验证、CSRF 防护。不自己实现 OAuth 流程，避免安全漏洞和不必要的复杂度
- **风险与对策**：Auth.js v5 配置项较多，需要正确配置 callbacks 和 session 策略。严格按官方文档配置，保持最小配置集

### ADR-8：会话策略使用 JWT，不引入服务端 Session Store

- **选择**：使用 JWT 存储在 httpOnly + Secure + SameSite=Lax cookie 中，不引入 Redis 或数据库 session store
- **理由**：首版用户量小，无服务端 session 管理需求。JWT 状态化足够覆盖"识别用户 + 数据隔离"，且不增加外部依赖。Auth.js 默认策略就是 JWT，零额外配置
- **演进余地**：后续若需实时吊销会话或管理多设备，可切换为 database session strategy，API 层获取 session 的方式不变

### ADR-9：数据关联使用 users 表 + 现有表加 user_id FK

- **选择**：新增 users 表存储 Google 身份信息，在 assets、analysis_tasks、generation_tasks 表增加 user_id 外键
- **理由**：最直接的数据关联方式，查询时 WHERE 过滤即可实现隔离。不引入 RBAC、角色、权限表（首版只有登录/未登录两种状态）
- **风险与对策**：user_id 在现有表中允许 NULL（兼容已有匿名数据），新数据在应用层强制写入 userId。查询时统一加 WHERE user_id = ? 条件，NULL 数据自然被排除

### ADR-10：路由保护使用 Next.js Middleware 统一拦截

- **选择**：在现有 middleware.ts 中扩展认证拦截逻辑，页面路由和 API 路由统一守卫
- **理由**：Next.js Middleware 在 Edge 层执行，适合做认证前置检查。现有 middleware 已有 rate limiting 逻辑，扩展认证检查保持单一入口，避免在多个 API Route 中重复认证代码
- **风险与对策**：Middleware 运行在 Edge Runtime，不能直接访问数据库。通过验证 JWT 签名（不需要 DB 查询）完成认证，用户数据在 API Route 层通过 session userId 查询

### ADR-11：匿名数据不迁移，新数据强制关联用户

- **选择**：现有匿名数据的 user_id 保持 NULL，不迁移不展示。新创建的业务数据在应用层强制写入 userId
- **理由**：迁移匿名数据无法确定用户归属，且匿名数据量不大。不迁移是最简策略，避免引入数据归属错误的风险
- **演进余地**：后续若需迁移，可在用户明确确认后手动关联

### ADR-12：Rate Limit 从 IP 级升级为用户级

- **选择**：已登录用户按 userId 限流，未登录按 IP 限流。复用现有 in-memory 限流机制，仅调整 key 策略
- **理由**：引入用户身份后，用户级限流比 IP 级更精准，防止同一用户换 IP 滥用。改动量最小，不引入新的限流中间件
- **风险与对策**：in-memory 限流在多实例部署时不共享状态。首版单实例部署无影响；后续可迁移到 Redis-based 限流

### 3.x 待确认问题

所有待确认问题已解决：Google OAuth 凭证已获取；部署环境为 Vercel，支持 Edge Runtime；现有匿名数据量小，无需清理策略。

## 4. 用户流程与状态

### 4.1 主流程

```
首页（未登录）→ 点击 CTA → 触发 Google OAuth → 授权成功 → 创建/更新用户记录 → 跳转工作区 → 所有数据关联到用户 → 顶部显示用户头像

首页（已登录）→ 点击 CTA → 直接跳转工作区

首页（未登录）→ 点击右上角"登录"→ 触发 Google OAuth → 登录成功 → 停留在首页

工作区（已登录）→ 点击头像 → 展开下拉菜单 → 退出登录 → 回到首页，右上角恢复"登录"按钮
```

关键节点说明：

- CTA 按钮点击时判断登录状态：已登录直接跳转工作区，未登录触发 OAuth
- 右上角"登录"按钮始终触发 OAuth，登录后停留在首页
- OAuth 回调后自动创建/更新用户记录，用户无感知
- 退出登录后清除所有会话数据，回到首页

### 4.2 关键分支

| 分支 | 入口 / 触发条件 | 架构处理方式 |
| --- | --- | --- |
| 未登录访问工作区 | 直接访问 /workspace | Middleware 拦截，重定向到首页 |
| 未登录调用业务 API | 直接调用 /api/analysis 等 | Middleware 拦截，返回 401 |
| OAuth 授权被拒绝 | 用户在 Google 授权页取消 | 回到首页，展示"登录已取消"提示 |
| OAuth 回调失败 | Google 返回错误 | 回到首页，展示"登录失败"提示 |
| 会话过期 | JWT 过期 | API 返回 401，前端引导重新登录 |
| 退出登录 | 用户点击退出 | 调用 Auth.js signOut，清除 JWT cookie，跳转首页 |
| 多标签页退出不一致 | 一个标签页退出，另一个仍在操作 | 另一个标签页下次 API 调用时收到 401，引导重新登录 |

### 4.3 认证状态机

```
unauthenticated → authenticating（跳转 Google 授权页）→ authenticated
authenticating → auth_failed（授权失败/被拒绝）→ unauthenticated
authenticated → session_expired（JWT 过期）→ unauthenticated
authenticated → signed_out（用户主动退出）→ unauthenticated
```

关键规则：

- `unauthenticated` 状态下首页可正常浏览，CTA 和右上角均触发登录
- `authenticating` 是瞬时状态，对应 OAuth 重定向过程
- `authenticated` 状态下所有业务操作自动关联用户身份
- `session_expired` 时优先记住目标页面，重新登录后自动跳转

| 不引入的内容 | 原因 |
| --- | --- |
| 自建 OAuth 客户端 | Auth.js 已封装完整 OAuth 流程，自建引入安全风险和不必要复杂度 |
| 服务端 Session Store (Redis) | JWT 策略足够，首版无实时吊销需求（ADR-8） |
| RBAC / 角色权限表 | 首版只有登录/未登录两种状态 |
| 用户资料编辑 API / 页面 | 需求明确不做 |
| 多 Provider 抽象层 | 首版只接 Google，不需要 Provider 注册中心 |
| 匿名数据迁移脚本 | 需求明确不迁移（ADR-11） |
| 独立的刷新 Token 机制 | Auth.js JWT 策略内置自动续期，7 天有效期足够 |
| 多设备管理 | 首版不需要 |

## 6. 运行链路

### 6.1 Google OAuth 登录

1. 用户点击 CTA 或右上角"登录"按钮
2. 前端调用 Auth.js `signIn('google')`，附带目标跳转页面（CTA → workspace，登录按钮 → 首页）
3. 浏览器重定向到 Google 授权页
4. 用户授权后，Google 重定向到 `/api/auth/callback/google`
5. Auth.js 交换 authorization code 获取 access token 和用户信息
6. Auth.js signIn callback 中：调用 User Repository，按 `google_id` 查找或创建用户记录
7. Auth.js 签发 JWT（包含 userId、email、name、avatarUrl），写入 httpOnly cookie
8. 重定向到步骤 2 中指定的目标页面

这条链路的实现原则：

- 整个 OAuth 流程由 Auth.js 编排，不自建 redirect/callback 逻辑
- 用户信息以 Google 返回的 id_token 为准，不额外调用 Google UserInfo API
- 首次登录创建用户，再次登录更新 name 和 avatar_url（Google 信息可能变化）
- JWT payload 保持最小（userId、email、name、avatarUrl），不存 Google access token

### 6.2 认证后的业务操作

1. 浏览器发起业务请求（如 POST /api/analysis），携带 JWT cookie
2. Next.js Middleware 验证 JWT 签名和有效期
3. 若 JWT 无效或过期，返回 401；若有效，将 userId 注入请求上下文（通过请求头传递）
4. API Route 从请求上下文获取 userId
5. 创建数据时强制设置 user_id = userId
6. 查询数据时强制添加 WHERE user_id = userId 条件

这条链路的实现原则：

- 认证检查在 Middleware 层统一完成，API Route 不重复验证 JWT
- userId 通过 Auth.js 的 `auth()` 函数在 API Route 中获取，不从请求头手动解析
- 数据隔离通过 Repository 层的 WHERE 条件实现，不依赖调用方手动过滤
- NULL user_id 的匿名数据自动被 WHERE 条件排除，无需额外处理

### 6.3 退出登录

1. 用户点击下拉菜单中的"退出登录"
2. 前端调用 Auth.js `signOut()`
3. Auth.js 清除 JWT cookie
4. 前端清除本地缓存的用户状态
5. 重定向到首页

这条链路的实现原则：

- 退出登录是前端驱动的操作，不需要服务端 API
- 如果退出请求失败，前端仍然清除本地状态，确保用户感知到"已退出"
- 退出后所有正在进行的轮询和请求都会因 401 而自动停止

## 7. 领域对象与关键契约

### 7.1 核心对象

| 对象 | Source of Truth | Owner | 用途 |
| --- | --- | --- | --- |
| User | PostgreSQL `users` 表 | Auth API | 用户身份记录，Google 账号与应用的映射 |
| Session | JWT cookie（Auth.js 管理） | Auth API | 会话状态，包含用户标识信息 |
| Asset (改造) | PostgreSQL `assets` 表 | Upload API / Generation API | 增加 user_id，关联到创建者 |
| AnalysisTask (改造) | PostgreSQL `analysis_tasks` 表 | Analysis API | 增加 user_id，关联到创建者 |
| GenerationTask (改造) | PostgreSQL `generation_tasks` 表 | Generation API | 增加 user_id，关联到创建者 |

### 7.2 推荐最小 Schema

```typescript
// 用户记录
interface User {
  id: string                          // ULID
  googleId: string                    // Google sub（唯一标识）
  email: string                       // Google 邮箱
  name: string                        // Google 显示名称
  avatarUrl: string | null            // Google 头像 URL
  createdAt: string                   // ISO 8601
  updatedAt: string                   // ISO 8601
}

// JWT Session Payload（Auth.js 管理，应用层只读）
interface SessionPayload {
  userId: string                      // 对应 User.id
  email: string
  name: string
  avatarUrl: string | null
}

// Asset (改造) — 新增 user_id
interface Asset {
  id: string                          // ULID
  userId: string | null               // 新增，旧匿名数据为 null
  type: 'reference' | 'generated'
  fileUrl: string
  thumbnailUrl: string | null
  width: number
  height: number
  mimeType: string
  createdAt: string
}

// AnalysisTask (改造) — 新增 user_id
interface AnalysisTask {
  id: string                          // ULID
  userId: string | null               // 新增，旧匿名数据为 null
  sourceAssetId: string
  status: 'pending' | 'processing' | 'completed' | 'failed'
  recipe: VisualRecipe | null
  promptText: string | null
  negativePromptText: string | null
  rawResponse: string | null
  errorMessage: string | null
  errorStage: 'vision' | 'llm' | null
  createdAt: string
  updatedAt: string
}

// GenerationTask (改造) — 新增 user_id
interface GenerationTask {
  id: string                          // ULID
  userId: string | null               // 新增，旧匿名数据为 null
  analysisTaskId: string
  status: 'pending' | 'processing' | 'completed' | 'failed'
  promptSnapshot: string
  negativePromptSnapshot: string
  params: GenerationParams
  modelName: string
  resultAssetId: string | null
  errorMessage: string | null
  createdAt: string
  updatedAt: string
}
```

### 7.3 API 边界

| 接口 | 方法 | 用途 | 认证要求 |
| --- | --- | --- | --- |
| `/api/auth/[...nextauth]` | * | Auth.js 自动路由（登录、回调、退出等） | 公开（Auth.js 自管理） |
| `/api/upload/presign` | POST | 签发预签名上传 URL | 需登录 |
| `/api/analysis` | POST | 创建分析任务并触发分析 | 需登录 |
| `/api/analysis/:id` | GET | 查询分析任务状态和结果 | 需登录 + 仅能查自己的 |
| `/api/generation` | POST | 创建生成任务 | 需登录 |
| `/api/generation/:id` | GET | 查询生成任务状态和结果 | 需登录 + 仅能查自己的 |

现有 API 的变更说明：

| 接口路径 | 变更说明 |
| --- | --- |
| POST /api/upload/presign | 请求体不变，服务端从 session 获取 userId 写入 Asset |
| POST /api/analysis | 请求体不变，服务端从 session 获取 userId 写入 Asset 和 AnalysisTask |
| GET /api/analysis/:id | 新增鉴权：验证 task 的 userId 是否匹配当前用户 |
| POST /api/generation | 请求体不变，服务端从 session 获取 userId 写入 GenerationTask |
| GET /api/generation/:id | 新增鉴权：验证 task 的 userId 是否匹配当前用户 |

### 7.4 状态流转

认证状态：

```
unauthenticated → authenticating → authenticated
authenticating → auth_failed → unauthenticated
authenticated → session_expired → unauthenticated
authenticated → signed_out → unauthenticated
```

用户记录生命周期：

```
首次 OAuth 成功 → 创建 User 记录
再次 OAuth 成功 → 更新 name 和 avatar_url
（用户记录永不删除，只通过退出登录清除会话）
```

### 7.5 数据边界

| 存储层 | 存储内容 | 职责边界 |
| --- | --- | --- |
| PostgreSQL — users 表 | 用户身份（google_id, email, name, avatar_url） | 用户身份的 source of truth |
| JWT cookie (httpOnly) | 会话信息（userId, email, name, avatarUrl） | 请求级身份验证，不存敏感凭证 |
| PostgreSQL — 业务表 | 资产、分析任务、生成任务（含 user_id） | 业务数据关联用户 |
| 浏览器内存 | 前端用户状态（登录态、用户信息） | UI 展示，source 为 JWT cookie |

**不存储的内容**：

- Google access token / refresh token（不存储，Auth.js 默认不持久化 OAuth token）
- 用户密码（Google OAuth 不涉及密码）
- 会话历史 / 登录设备信息

### 7.6 命名与标识规则

延续 01 期规则（ULID、camelCase JSON、snake_case DB），新增：

| 业务概念 | 代码 / API 术语 | 说明 |
| --- | --- | --- |
| 用户 | `User` | 不使用 `Account`、`Profile`、`Member` |
| Google 唯一标识 | `googleId` | 不使用 `sub`、`providerId` |
| 用户 ID 外键 | `userId` | 数据库中为 `user_id`，TypeScript 中为 `userId` |
| 会话 | `session` | 不使用 `token`、`credential` |
| 登录 | `signIn` | 对应 Auth.js API，不使用 `login` |
| 退出登录 | `signOut` | 对应 Auth.js API，不使用 `logout` |

## 8. 非功能需求、风险与运行策略

### 8.1 性能与吞吐量目标

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| OAuth 登录耗时 | <= 5 秒 | 从点击登录到进入工作区 |
| JWT 验证耗时 | <= 5ms | Middleware 层验证，不涉及 DB 查询 |
| 认证后 API 额外耗时 | <= 1ms | 仅增加 userId 条件，无额外查询 |
| 会话有效期 | 7 天 | 过期后需重新登录 |
| 首版预期并发 | <= 20 个同时在线用户 | 灰度阶段 |

### 8.2 可靠性、错误处理与降级策略

基础错误处理：

- OAuth 授权被拒绝：回到首页，展示"登录已取消"提示
- OAuth 回调失败：回到首页，展示"登录失败，请重试"提示
- 会话过期：API 返回 401，前端引导重新登录
- 用户数据关联失败：整个事务回滚，不创建孤立数据
- 退出登录失败：前端清除本地会话，展示"已退出"状态

降级策略：

| 级别 | 触发条件 | 系统行为 | 用户可见影响 |
| --- | --- | --- | --- |
| L1 | Google OAuth 暂时不可用 | 首页正常展示，登录/CTA 提示"登录服务暂时不可用" | 无法登录，但可浏览首页 |
| L2 | JWT 密钥配置异常 | 认证失败，所有用户被引导重新登录 | 需重新登录 |
| L3 | 认证系统完全不可用 | 通过配置开关临时开放匿名访问模式 | 回退到 01 期行为 |

### 8.3 安全与反滥用策略

| 项目 | 首版策略 |
| --- | --- |
| OAuth 安全 | Auth.js 内置 state 参数防 CSRF；httpOnly + Secure + SameSite=Lax cookie 防 XSS 和 CSRF |
| JWT 安全 | 签名密钥通过环境变量注入，不硬编码；JWT payload 不含敏感凭证 |
| 数据隔离 | 所有查询强制 WHERE user_id = ?，Repository 层封装为基础方法，不依赖调用方手动过滤 |
| Rate Limit | 已登录用户按 userId 限流，未登录按 IP 限流（复用现有机制，ADR-12） |
| Google Token | 不存储 Google access/refresh token，仅提取用户信息 |
| 信息泄露防护 | 错误提示不暴露内部错误详情；JWT payload 仅含必要展示信息 |

### 8.6 主要风险

| 风险 | 影响 | 缓解方式 |
| --- | --- | --- |
| OAuth 回调 URL 配置错误 | 登录完全不可用 | 部署前验证 Google Console 配置；开发环境使用 ngrok 测试回调 |
| JWT 密钥泄露 | 会话伪造 | 密钥通过环境变量管理，不提交代码库；密钥轮换后所有会话自动失效 |
| 数据隔离代码遗漏 | 用户数据泄漏 | Repository 层封装隔离逻辑，强制所有查询带 user_id 条件；代码 review 重点检查 |
| 现有功能回归 | 01 期闭环被破坏 | 迁移时 user_id 允许 NULL 兼容旧数据；增加 E2E 测试覆盖完整创作流程 |
| 会话过期导致用户操作中断 | 用户体验差 | 前端拦截 401，引导重新登录后恢复到目标页面 |

## 9. 实施建议与技术选型

### 9.1 推荐核心技术栈

| 分层 | 选型 | 选型说明 |
| --- | --- | --- |
| 认证框架 | Auth.js v5 (NextAuth) | Next.js 生态最成熟的认证方案，内置 Google Provider 和 JWT 策略 |
| OAuth Provider | Google OAuth 2.0 | 需求明确只支持 Google 登录 |
| 会话管理 | JWT (httpOnly cookie) | Auth.js 默认策略，无额外依赖 |
| 数据库迁移 | SQL 脚本 + 手动执行 | 延续 01 期策略，不引入迁移工具 |

### 9.2 阶段划分建议

#### Phase A：认证基础

- 安装和配置 Auth.js v5
- Google OAuth Client 配置
- users 表创建
- 登录/回调/退出流程跑通
- JWT session 签发和验证
- User Repository（查找或创建）

验证目标：能通过 Google 登录，获取用户信息，JWT 正确签发和验证。

#### Phase B：路由守卫与数据关联

- Middleware 认证拦截（页面 + API）
- 现有业务表增加 user_id 字段
- Repository 层改造（创建时写入 userId，查询时过滤 userId）
- 前端用户状态管理（登录态检测、用户信息展示）

验证目标：未登录无法访问工作区和调用业务 API；已登录用户的数据正确关联和隔离。

#### Phase C：UI 集成与验收

- 导航栏用户头像和下拉菜单
- CTA 按钮登录触发逻辑
- 会话过期处理
- 错误提示和降级
- E2E 测试覆盖认证流程

验证目标：完整用户旅程验收通过，01 期创作闭环不受影响。

## 10. 架构结论

本期架构围绕 **OAuth → Identify → Isolate** 核心目标设计，关键判断如下：

1. **Auth.js 是最简实现路径**：不自建 OAuth 客户端，不引入 Session Store，用 Auth.js + JWT 完成全部认证需求。零新增外部依赖，零新增付费服务。

2. **数据关联策略极简**：新增 users 表 + 现有表加 user_id FK。不引入角色权限体系，不做匿名数据迁移。首版只有"登录"和"未登录"两种状态。

3. **安全是底线而非目标**：httpOnly cookie、JWT 签名验证、CSRF 防护、数据隔离——这些都是 Auth.js 或框架内建能力，不是额外开发项。唯一需要人工保证的是 Repository 层的 WHERE user_id 条件不遗漏。

4. **渐进式改造 01 期代码**：不重写现有 API，而是在 Middleware 层增加认证检查，在 Repository 层增加 userId 参数。改造量可控，01 期功能不受影响。

5. **回退方案明确**：通过配置开关可临时关闭认证要求，回退到 01 期匿名模式。任何认证问题不影响首页展示。
