# 架构设计文档：Prompt 模板化与变量系统

_本文件只保留当前版本真正影响实现的架构决策、边界和契约；DDL、目录树、环境变量、实施故事等内容默认不放入正文。_

## 1. 系统摘要

Prompt 模板化与变量系统，在已有 **Reference → Recipe → Render** 工作台基础上新增 **Template** 能力层。用户将分析后的 prompt 保存为参数化模板（支持 `{{variableName}}` 变量语法），通过向导式填值快速复用风格配置生成新图。

核心闭环：**Recipe → Template → Render**

首版验证目标：证明「模板保存 → 变量填值 → 一键生成」的闭环能显著降低同风格换主体的操作成本。

## 2. 范围、非目标与成功标准

### 2.1 P0 范围

- 模板数据持久化（`templates` 数据表 + 后端 CRUD 接口）
- 从分析结果「保存为模板」入口（指令编辑区内操作按钮）
- 模板编辑器（名称输入 + prompt 文本编辑 + 变量插入工具栏）
- 变量插入交互（工具栏按钮 → 配置变量名/默认值 → 插入 `{{var}}` 到光标位置）
- 模板列表面板（右侧抽屉 ~320px，展示名称、变量数、创建时间）
- 加载模板到指令编辑器
- 删除模板（含确认对话框）

### 2.2 P1 预留

- 变量向导填值 UI（加载模板后自动识别变量，表单填值后替换生成最终 prompt）
- 模板管理增强（重命名、复制模板）

### 2.3 明确不做

- 预设模板库 / 系统内置通用风格模板
- 模板分类 / 标签体系
- 模板导入 / 导出
- 模板分享 / 社区功能
- 批量生成（一次填值 → 多组变体）
- 与 ComfyUI 工作流互导入
- 模板版本历史

### 2.4 成功标准

| 指标 | 首版目标 |
| --- | --- |
| 模板 CRUD 功能正常 | 创建/列表查询/详情查询/删除四项操作均可正常完成，无数据丢失或状态异常 |
| 变量提取与替换正确 | 从模板正文正确提取所有合法 `{{var}}` 标记；按长变量名优先顺序替换后结果符合预期 |
| 端到端闭环可走通 | 保存 → 列表 → 加载 → （P1）填值 → 生成新图，全路径无断裂 |
| 模板加载响应 | <= 500ms（单次查询 + 渲染） |
| 首版预期并发 | <= 20 个同时在线用户 |

## 3. 关键架构决策（ADR）

### ADR-1：模板存储于 PostgreSQL 新建 `templates` 表

- **选择**：新建独立 `templates` 表，使用 JSONB 存储变量定义列表，与现有 `assets` / `analysis_tasks` / `generation_tasks` 表并列
- **理由**：模板是独立的领域实体，有自身的生命周期和属性（名称、正文、变量列表、来源追溯）；独立表支持结构化查询（按名称搜、按创建时间排序）、索引优化和未来扩展；JSONB 存储变量定义天然支持后续增加 type/hint/options 字段而不需要 DDL 变更
- **演进余地**：若后续需要模板版本历史，可新增 `template_versions` 表；若需要模板分类标签，可加关联表或 JSONB 数组字段

### ADR-2：变量机制采用「正则提取 + 字符串替换」，不做模板引擎引入

- **选择**：用正则 `/{{([a-zA-Z_]\w*)}}/g` 从模板正文提取变量标记，替换时按变量名长度降序执行全局字符串替换；不引入 Mustache / Handlebars 等模板引擎库
- **理由**：本期变量语义极简——仅做纯文本占位符替换，无条件判断、循环、嵌套等需求；引入模板引擎增加包体积和学习成本，且其转义规则可能与 D-08 的「纯文本处理」原则冲突；正则方案代码量 < 50 行，完全可控
- **风险与对策**：用户在变量值中输入 `{{anotherVar}}` 不会触发二次替换（单次策略），已知限制已在 PRD D-08 中明确声明；若后续需要表达式语法（如 `{{var \| default}}`），再评估是否引入轻量模板引擎

### ADR-3：模板 API 采用 RESTful CRUD，4 个端点覆盖全量操作

- **选择**：`POST /api/templates`（创建）、`GET /api/templates`（列表）、`GET /api/templates/:id`（详情）、`DELETE /api/templates/:id`（删除）；P1 阶段追加 `PUT /api/templates/:id`（更新/重命名）和 `POST /api/templates/:id/duplicate`（复制）
- **理由**：模板是标准 CRUD 实体，RESTful 映射清晰；4 个端点对应 P0 用户故事的一一映射（US-01 创建、US-03+US-05 列表查询、US-04 删除）；不引入 GraphQL 或 RPC，首版端点数量少且关系简单
- **演进余地**：若后续需要复杂查询（按变量名搜索、按来源分析任务筛选），可在 GET 列表接口上加 query params，不需要新端点

### ADR-4：变量定义作为模板正文的派生数据，不独立维护一致性

- **选择**：变量定义列表（`variables` JSONB 字段）在保存模板时从正文文本中自动提取生成，加载时以正文为 source of truth；前端编辑器中插入/修改变量时同步更新正文文本，不维护独立的「变量状态 → 正文渲染」双向绑定
- **理由**：避免「变量定义与正文中的 `{{var}}` 标记不一致」的状态同步问题；正文文本是唯一的真实来源，变量列表只是便于前端展示的派生视图；降低前端状态管理复杂度
- **风险与对策**：如果用户直接在文本中手写或删除 `{{var}}` 而未通过变量工具栏操作，保存时重新提取会自动修正变量列表，保证最终一致性

### ADR-5：模板面板 UI 采用 Drawer 组件 + 内嵌向导双组件架构

- **选择**：模板列表以右侧 Drawer（~320px）呈现；变量向导以独立 Panel 组件内嵌于右列指令编辑区位置（替换原编辑器内容区）；两者为独立 React 组件，通过回调函数与 workspace 主页面通信
- **理由**：Drawer 不遮挡左中两列核心工作区（参考图 + 风格拆解）；内嵌向导保持生成参数设置区域不变，空间利用高效；组件独立便于测试和维护；符合 PRD D-05 的布局决策
- **演进余地**：小屏幕下 Drawer 可折叠为底部 Sheet 或全屏模态（响应式策略留待 P1 后评估）

### ADR-6：模板与用户归属沿用现有 userId 关联模式

- **选择**：`templates` 表包含 `userId` 外键关联 `users` 表，所有查询和写操作均校验 userId 归属；与现有 `analysis_tasks` / `generation_tasks` / `assets` 的权限模式完全一致
- **理由**：保持数据模型的一致性，不引入新的权限抽象层；首版已具备 auth 基础设施（NextAuth），直接复用 session 中的 userId
- **演进余地**：若后续需要模板共享/协作，可增加 `visibility` 字段（private/team/public）和共享关联表

### ADR-7：「保存为模板」读取当前编辑器内容而非分析任务快照

- **选择**：点击「保存为模板」时，取指令编辑器当前的文本内容（可能已被用户编辑过）作为模板正文，而非从 `analysis_tasks.promptText` 取原始 AI 生成结果
- **理由**：用户保存模板的意图通常是保存「我调整后满意的这个版本」，而非 AI 的原始输出；编辑器内容才是用户认可的最新状态
- **风险与对策**：若编辑器为空（用户清空了 prompt），需提示「prompt 内容不能为空」；需要在保存接口入参中传入 promptText，而非依赖后端从 analysisTaskId 回查

## 4. 用户流程与状态

### 4.1 主流程

```
工作区完成分析 → 编辑 prompt 满意 → 点击「保存为模板」→ 弹出模态对话框 →
输入模板名称 → 在 prompt 文本中插入 {{变量}} 标记 → 确认保存 →
（后续会话）打开模板抽屉 → 选择模板 → 加载到编辑器 → （P1）变量向导填值 → 生成新图
```

关键节点说明：

- 「保存为模板」取编辑器当前文本内容，非分析任务原始快照
- 保存时自动从正文提取所有 `{{var}}` 构建变量定义列表
- 加载模板时默认将原文（含 `{{var}}` 标记）填充到编辑器
- P1 阶段：检测到变量时自动触发出导面板，跳过后恢复普通编辑态

### 4.2 关键分支

| 分支 | 入口 / 触发条件 | 架构处理方式 |
| --- | --- | --- |
| 变量格式异常 | 模板正文含未闭合 `{{` / `}}` 或嵌套标记 | 不阻断加载，原样显示文本 + 编辑器顶部轻量警告条 |
| 删除模板 | 用户在模板列表点击删除 | 弹出确认对话框（含模板名称），确认后物理删除 |
| 模板名称重复 | 用户保存时输入了已有名称 | 返回 409 冲突错误，前端提示「已存在同名模板」 |
| 编辑器内容为空 | 用户在空编辑器状态下点保存 | 前端拦截，提示「请先输入 prompt 内容」 |
| 向导跳过 | 用户在变量向导中点击「跳过」 | 恢复为含 `{{var}}` 标记的普通编辑态，用户可手动编辑 |
| 模板列表为空 | Drawer 打开时 GET 列表返回空数组 | 显示空状态引导（插图 + "还没有保存过模板…"文案），提示用户先完成分析再保存模板 |

### 4.3 模板功能前端状态机

```
workspace 正常态 ↔ 模板保存对话框（模态）
workspace 正常态 ↔ 模板列表面板（Drawer 开/关）
workspace 正常态 ↔ 变量向导面板（内嵌替换编辑区，P1）
```

关键规则：

- 模板保存对话框为模态，打开时阻断 workspace 交互
- 模板 Drawer 为非模态，可与 workspace 同时操作（如查看风格拆解的同时选模板）
- 变量向导面板与 Drawer 互斥：打开向导时自动关闭 Drawer
- 所有模板相关状态在关闭/取消时不影响 workspace 已有数据（分析结果、生成结果等）

### 5.3 需要刻意避免的过度设计

| 不引入的内容 | 原因 |
| --- | --- |
| 独立模板引擎库（Mustache/Handlebars） | 本期仅需纯文本占位符替换，正则足够（ADR-2） |
| 模板版本历史表 | 首版无版本回溯交互，需要时可从操作日志反向提取 |
| 模板分类/标签体系 | P0/P1 无分类需求，过早引入增加列表复杂度 |
| 模板导入/导出功能 | 首版数据量小，云端存储即可满足跨设备需求 |
| 模板共享/权限系统 | 涉及用户体系和团队概念，范围过大 |
| 变量类型系统（type/hint/options） | MVP 仅 name + defaultValue 够用，JSONB 天然支持后续扩展 |
| 服务端模板渲染端点 | 替换逻辑在前端执行即可，无需服务端参与 |

## 6. 运行链路

### 6.1 保存模板

1. 用户在指令编辑器中编辑完 prompt，点击「保存为模板」按钮
2. 前端弹出模态对话框，预填充当前编辑器文本内容
3. 用户输入模板名称（必填），可选地在文本中插入 `{{变量名}}` 标记
4. 用户点击「保存模板」按钮
5. 前端调用 `POST /api/templates`，传入 `{ name, content, sourceAnalysisTaskId? }`
6. API 校验：userId 来自 session，name 非空且长度 1–50，content 非空
7. API 检查同名模板是否存在（同一 userId 下），存在则返回 409
8. API 用正则从 content 中提取所有 `{{var}}` 标记，按变量名去重（Set 语义，保留首次出现的 defaultValue），构建变量定义列表（若用户未通过工具栏为某变量设置 defaultValue，则默认为空字符串 `''`）
9. API 写入 `templates` 表，返回完整模板记录
10. 前端显示成功提示，关闭对话框

这条链路的实现原则：

- `content` 字段来自编辑器当前文本（用户可能已编辑过），不是 analysisTasks.promptText 快照
- `sourceAnalysisTaskId` 为可选字段，前端在有活跃分析任务时传入
- 变量提取在后端保存时一次性完成，前端不负责构建 variables 字段
- 同名校验基于 userId + name 的唯一性约束

### 6.2 加载模板

1. 用户点击「我的模板」按钮，打开右侧 Drawer
2. 前端调用 `GET /api/templates?page=1&pageSize=20`，获取当前用户的模板列表（按创建时间倒序）
3. Drawer 渲染模板卡片列表（名称、变量数量、创建时间）
4. 用户点击某模板卡片的「使用」按钮
5. 前端调用 `GET /api/templates/:id` 获取模板详情（或直接用列表数据）
6. 将模板的 `content` 字段填充到指令编辑器
7. 关闭 Drawer
8. （P1）前端检测 content 中是否含 `{{var}}` 标记：
   - 含变量 → 在右列编辑区位置渲染变量向导面板
   - 不含变量 → 直接进入正常编辑态

这条链路的实现原则：

- 列表接口返回精简字段（id, name, variableCount, createdAt），不含完整 content；支持分页（page + pageSize 参数，默认 pageSize=20）
- 详情/使用时才返回 content（减少列表传输量）
- 变量检测在前端用同一正则执行，与后端提取逻辑保持一致
- P1 向导的替换逻辑也在前端执行（纯文本操作，无需服务端参与）

### 6.3 删除模板

1. 用户在模板列表中点击某卡片的「···」→「删除」
2. 前端弹出确认对话框：「确定删除模板"XXX"？删除后不可恢复。」
3. 用户确认 → 前端调用 `DELETE /api/templates/:id`
4. API 校验 userId 归属后物理删除记录
5. 前端从本地列表中移除该项，刷新显示

这条链路的实现原则：

- 删除为物理删除（无回收站/软删除），与 PRD 定义一致
- 必须二次确认，防止误操作
- 删除失败时保留原列表状态，提示错误原因

## 7. 领域对象与关键契约

### 7.1 核心对象

| 对象 | Source of Truth | Owner | 用途 |
| --- | --- | --- | --- |
| PromptTemplate | PostgreSQL `templates` 表 | Template API | 承载模板元数据、正文内容和变量定义 |
| TemplateVariable | `templates.variables` JSONB 字段（派生自正文） | 变量解析模块 | 描述模板中的可替换变量（name + defaultValue） |

### 7.2 推荐最小 Schema

```typescript
/** 模板变量定义 */
interface TemplateVariable {
  name: string;           // 变量名，匹配 [a-zA-Z_]\w* 格式
  defaultValue: string;   // 默认值，用户未填值时使用
}

/** Prompt 模板 */
interface PromptTemplate {
  id: string;                        // ULID
  name: string;                      // 模板名称，1-50 字符
  content: string;                   // 模板正文（含 {{var}} 标记的 prompt 文本）
  variables: TemplateVariable[];     // 变量定义列表（从 content 自动提取）
  sourceAnalysisTaskId: string | null; // 来源分析任务编号（可为 null）
  userId: string;                    // 所属用户 ID
  createdAt: Date;
  updatedAt: Date;
}
```

### 7.3 API 边界

| 接口 | 方法 | 用途 | 请求体 | 数据来源说明 |
| --- | --- | --- | --- | --- |
| `/api/templates` | POST | 创建模板 | `{ name, content, sourceAnalysisTaskId? }` | name: user_input, content: user_input(编辑器当前文本), sourceAnalysisTaskId: frontend_computed(上下文中获取) |
| `/api/templates` | GET | 模板列表（分页） | query: page, pageSize（默认 20） | — |
| `/api/templates/:id` | GET | 模板详情 | — | id: path_param |
| `/api/templates/:id` | DELETE | 删除模板 | — | id: path_param |

共 4 个端点，覆盖 P0 全部用户故事。

**响应格式约定**：

- 成功创建：`201 { id, name, content, variables, sourceAnalysisTaskId, createdAt }`
- 列表：`200 [{ id, name, variableCount, createdAt }]`（不含 content）
- 详情：`200 { id, name, content, variables, sourceAnalysisTaskId, createdAt, updatedAt }`
- 删除成功：`204 No Content`
- 错误统一格式：`{ error, code }`（与现有 API 一致）

### 7.4 状态流转

模板是无状态实体（非流程型对象），无状态机。生命周期为：

```
创建 → 存在 → （更新 P1）/ 删除
```

规则：
- 创建时自动提取变量列表，后续不再自动同步（除非通过更新接口重新保存）
- 删除为不可逆物理删除
- 名称唯一性约束范围：同一 userId 下

### 7.5 数据边界

| 存储层 | 存储内容 | 职责边界 |
| --- | --- | --- |
| PostgreSQL `templates` 表 | 模板元数据、正文、变量定义（JSONB） | 模板数据的 source of truth |
| PostgreSQL 现有表（不变） | assets, analysis_tasks, generation_tasks | 不变 |
| 浏览器内存 | 当前编辑器文本、模板 Drawer 开关状态、向导填值中间态 | 会话级临时状态 |
| 对象存储 R2（不变） | 参考图和生成图 | 不变 |

### 7.6 命名与标识规则

- **ID 策略**：ULID，与现有实体一致，不加类型前缀
- **JSON 命名**：camelCase（前端和 API 统一）
- **数据库命名**：snake_case
- **术语映射**：

| 业务概念 | 代码 / API 术语 | 说明 |
| --- | --- | --- |
| 模板 | `PromptTemplate` / `template` | 不使用 `style`、`recipe`、`profile` |
| 模板正文 | `content` | 不使用 `promptText`、`body`、`templateText`（避免与 AnalysisTask.promptText 混淆） |
| 变量标记 | `{{variableName}}` | Mustache 风格，PRD D-01 确认 |
| 变量定义 | `TemplateVariable` | 包含 name + defaultValue |
| 来源分析任务 | `sourceAnalysisTaskId` | 可选外键引用 |
| 变量数量 | `variableCount` | 列表接口中的聚合字段（variables.length） |

## 8. 非功能需求、风险与运行策略

### 8.1 性能与吞吐量目标

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 保存模板 API 耗时 | <= 200ms | 纯数据库写入 + 正则提取，无外部调用 |
| 模板列表查询 | <= 100ms | 单表查询 + userId 索引，分页返回（默认 20 条/页） |
| 模板详情查询 | <= 50ms | 主键查询 |
| 变量提取（正则） | <= 10ms | 单次正则匹配，模板长度通常 < 2000 字符 |
| 变量替换 | <= 10ms | 字符串 replace，变量数通常 < 10 个 |
| 首版预期并发 | <= 20 个同时在线用户 | 与主系统一致 |

### 8.2 可靠性、错误处理与降级策略

基础错误处理：

- 保存失败（网络/服务器）：前端提示错误，保留对话框内容不丢失，用户可重试
- 名称重复（409）：前端提示「已存在同名模板」，用户修改名称后重试
- 删除失败：保留原列表状态，提示错误原因
- 变量格式异常：不阻断加载，原样显示 + 轻量警告条

模板功能本身无外部依赖（纯数据库操作），因此没有传统意义上的降级链。最坏情况：

| 级别 | 触发条件 | 系统行为 | 用户可见影响 |
| --- | --- | --- | --- |
| L1 | 数据库写入延迟 | 请求超时后前端提示重试 | 保存/删除稍慢 |
| L2 | 数据库不可用 | 模板 CRUD 全部不可用，返回 503 | 无法保存/加载模板，但工作区的分析和生成能力不受影响（模板是附加功能，非核心链路） |

### 8.3 安全与反滥用策略

| 项目 | 首版策略 |
| --- | --- |
| 认证 | 复用现有 NextAuth session，所有模板接口校验 userId |
| 归属校验 | 所有读写操作带 userId WHERE 条件，防止跨用户数据访问 |
| 输入校验 | name: 1-50 字符；content: 非空，长度上限 10000 字符；变量名: 正则白名单校验 |
| Rate Limit | 模板创建 30 次/小时/IP（远低于分析/生成的限制，因为模板操作成本低） |
| XSS 防护 | 模板名称和变量默认值在渲染前做 HTML 转义（React JSX 默认转义）；content 作为 textarea/prompt 文本展示，不渲染为 HTML |
| API Key | 无涉及（模板功能不调用外部 AI 服务） |

### 8.4 成本控制预期

模板功能本身不引入新的按量计费服务（纯数据库操作）。成本影响：

| 项目 | 预估单次成本 | 首版控制策略 |
| --- | --- | --- |
| PostgreSQL 存储 | < $0.01/月（单表，数据量极小） | 不设清理策略，数据量可控 |
| 无外部 API 调用 | $0 | — |

### 8.5 可观测性

最小可观测方案（延续现有模式）：

- **应用日志**：每个模板 API 请求记录 templateId/name、userId、耗时、操作类型（create/list/get/delete）、错误信息
- **前端埋点**：覆盖最小埋点集：`template_save_clicked`、`template_saved`、`template_loaded`、`template_deleted`、`wizard_applied`（P1）
- **告警**：模板操作错误率连续 1 小时超过 5% 时触发告警（阈值低于主链路，因为模板是附加功能）

### 8.6 主要风险

| 风险 | 影响 | 缓解方式 |
| --- | --- | --- |
| 用户在模板正文中手写非法变量名格式 | 变量提取遗漏或向导填值不完整 | 保存时后端正则只提取合法格式，非法标记被视为普通文本；前端编辑器中对合法 `{{var}}` 高亮显示，引导用户使用正确格式 |
| 模板 content 过长（> 10000 字符） | 数据库存储和传输开销增大 | 前端做长度校验提示；实际场景中 prompt 通常 < 2000 字符 |
| 同一变量名多次出现，用户希望每次填不同值 | 只能统一替换为同一值 | 已知限制，PRD 明确声明不在本期处理；UI 上可在向导中标注「出现 N 次」提示用户 |
| 用户在变量值中输入含 `{{` 或 `}}` 的文本 | 可能干扰视觉识别但不影响替换正确性 | 替换按长变量名优先顺序执行，已完成替换的位置不会被二次扫描；D-08 已明确单次替换策略 |

## 10. 架构结论

本架构围绕 **Recipe → Template → Render** 扩展闭环设计，关键判断如下：

1. **模板是独立领域实体**：新建 `templates` 表而非复用 `analysis_tasks` 的字段扩展，因为模板有自己的生命周期、归属和变量语义（ADR-1）。

2. **变量机制极简**：正则提取 + 字符串替换，不引入模板引擎。本期变量只有「占位符替换」一个语义，过度工程化反而增加维护成本和边界情况（ADR-2）。

3. **纯数据库操作，零外部依赖**：模板功能不调用任何 AI 服务或外部 API，故障隔离性好——即使模板功能不可用，核心的分析和生成链路完全不受影响（8.2 L2 降级）。

4. **UI 组件独立解耦**：Drawer、保存对话框、变量向导各自为独立组件，通过回调与 workspace 主页面通信，便于单独测试和迭代（ADR-5）。

5. **完全复用现有技术栈**：无新增 npm 依赖，无新增基础设施，开发成本集中在业务逻辑和 UI 组件上。

6. **清晰的演进路径**：JSONB 变量定义支持后续扩展 type/hint/options；独立表支持版本历史和分类标签；RESTful 接口支持复杂查询参数扩展。每个决策都保留了合理的演进余地，但首版不为假设场景付出成本。
