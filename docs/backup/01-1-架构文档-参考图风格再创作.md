# 架构设计文档：参考图风格提取与再创作

_本文件只保留当前版本真正影响实现的架构决策、边界和契约；DDL、目录树、环境变量、实施故事等内容默认不放入正文。_

## 1. 系统摘要

视觉风格提取与再创作工作台。用户上传参考图后，系统通过两阶段 AI 链路（视觉理解 + LLM 结构化整理）提取可编辑的结构化视觉配方，用户确认或编辑后一键生成同风格新图。

核心闭环：**Reference → Recipe → Render**

首版验证目标：证明"结构化视觉配方"能稳定驱动同风格再创作，而不是做普通图转 Prompt 工具。

## 2. 范围、非目标与成功标准

### 2.1 P0 范围

- 上传单张参考图
- 两阶段 AI 分析（视觉理解 + 结构化整理），输出结构化视觉配方
- Prompt / Negative Prompt 自动生成
- Prompt 编辑
- 单模型图片生成
- 参考图与生成结果对比
- 基于结果继续迭代生成
- 首页价值展示与上传入口

### 2.2 P1 预留

- 风格强度滑杆
- 主体替换
- 示例图快速体验
- 轻量历史记录

### 2.3 明确不做

- 多模型深度适配与 Provider 注册中心
- 团队协作与权限分层
- 风格模板库、品牌风格包
- 批量上传、多图融合、LoRA 训练
- 社区、模板市场、开放 API
- 完整账号体系（首版不强制登录）

### 2.4 成功标准

| 指标 | 首版目标 |
| --- | --- |
| 分析完成率 | >= 95% |
| 生成完成率 | >= 95% |
| 首轮闭环完成率 | >= 35% |
| Prompt 直接采纳或轻编辑后使用率 | >= 60% |
| 上传到首张结果图中位耗时 | <= 90 秒 |
| 分析结果主观有效性 | >= 70% |

## 3. 关键架构决策（ADR）

### ADR-1：全栈框架选择 Next.js 单体

- **选择**：使用 Next.js 同时承载前端页面和 API Routes，不拆独立后端服务
- **理由**：首版只有首页和工作区两个页面，API 端点不超过 6 个，拆服务只增加部署和联调成本。Next.js API Routes 足够承载当前业务复杂度
- **演进余地**：若后续 API 复杂度增长或需要独立扩缩容，可将 API Routes 迁移为独立 Node 服务，路由契约不变

### ADR-2：两阶段 AI 链路串行执行

- **选择**：分析链路固定为"视觉理解模型 → LLM 结构化整理"两阶段串行调用，不做并行或单阶段合并
- **理由**：视觉模型负责看图提取原始信息，LLM 负责结构化整理和 Prompt 生成，职责清晰。单阶段方案在结构化稳定性上风险更高，并行方案在首版没有收益
- **风险与对策**：两阶段串行增加总耗时，但需求要求分析耗时 <= 30 秒，两阶段合计可控；若超限优先优化 Prompt 模板压缩输出，不改链路结构

### ADR-3：异步任务用数据库轮询，不引入消息队列

- **选择**：分析任务和生成任务状态存 PostgreSQL，前端定时轮询，不引入 Redis / Queue / Worker
- **理由**：首版并发量低，任务类型只有分析和生成两种，数据库轮询足够。引入消息队列增加运维和部署复杂度，首版 ROI 不成立
- **演进余地**：后续并发增长时，可加 Redis 队列 + Worker 进程，任务表结构不变，只改写入和消费方式

### ADR-4：文件上传使用预签名 URL 直传 Cloudflare R2

- **选择**：浏览器通过预签名 URL 直传 Cloudflare R2，图片二进制不经过业务 API
- **理由**：避免 API 层承受大文件传输的内存和带宽压力。预签名 URL 方案成熟，客户端实现简单
- **风险与对策**：预签名 URL 有时效限制，需设置合理有效期（建议 10 分钟）；上传完成后由客户端回调 API 确认

### ADR-5：结构化视觉配方作为核心中间层

- **选择**：系统核心产物是结构化视觉配方（VisualRecipe），不是一段 Prompt 文本。Prompt 由配方派生，配方是 source of truth
- **理由**：这是产品差异化的核心——"不只输出 Prompt，而是输出可编辑视觉配方"。围绕配方设计数据模型，才能支撑后续风格资产化
- **风险与对策**：配方 Schema 的字段定义需要前期确认，一旦灰度后频繁大改会影响已有数据。首版字段从需求文档提炼，保持扁平结构降低变更成本

### ADR-6：不引入 Prompt 版本表

- **选择**：不为 Prompt 编辑历史创建独立版本表，每次生成时将当前 Prompt 快照存入生成任务记录
- **理由**：首版用户编辑 Prompt 后直接生成，没有"回溯历史版本"或"对比多版本"的交互。独立版本表只增加写入复杂度，无前端消费场景
- **演进余地**：后续若需要版本管理，可从生成任务的快照反向提取，或新增版本表

### 3.x 已确认选型

已确认选型：

- 视觉理解模型：Gemini 3 Flash
- LLM 结构化整理：Gemini 3 Flash（首版与视觉理解统一 Provider，降低接入复杂度）
- 生图模型：fal.ai / FLUX.2
- 对象存储：Cloudflare R2
- 匿名会话持久化：首版不做，刷新页面后不恢复工作区状态

## 4. 用户流程与状态

### 4.1 主流程

```
首页 → 上传参考图 → 跳转工作区 → 系统自动分析（两阶段）→ 展示结构化配方 + Prompt → 用户确认或编辑 Prompt → 点击生成 → 展示结果图 → 对比参考图与结果 → 继续迭代或结束
```

关键节点说明：

- 上传完成后自动触发分析，不需要用户二次确认
- 分析完成后 Prompt 自动填充到编辑器，用户可直接生成
- 生成完成后默认进入对比视图，用户可从结果继续发起下一轮生成

### 4.2 关键分支

| 分支 | 入口 / 触发条件 | 架构处理方式 |
| --- | --- | --- |
| 示例图体验（P1） | 首页点击示例图 | 跳转工作区，直接加载预计算的分析结果，跳过分析阶段 |
| 分析结果不准确 | 用户认为分析偏差 | 用户编辑结构化字段或直接修改 Prompt，不重跑分析 |
| 替换参考图 | 工作区点击替换图片 | 清空当前分析和生成结果，重新走上传 + 分析流程 |
| 生成后继续迭代 | 查看结果后修改 Prompt | 以上一次生成参数为起点，不重跑分析，只提交新生成任务 |
| 分析 / 生成失败 | 外部模型报错或超时 | 保留已有稳定结果，展示失败原因和重试入口 |

### 4.3 工作区前端状态机

```
idle → uploading → analyzing → analysis_ready → generating → generation_ready

analysis_ready → generating（用户点击生成）
generation_ready → generating（用户修改后再次生成）

uploading / analyzing / generating → error
error → 回到上一个稳定状态（uploading 失败回 idle，analyzing 失败回 idle 并保留原图，generating 失败回 analysis_ready）
```

关键规则：

- `error` 不清空已有稳定结果，用户始终能看到最近一次成功的数据
- `generation_ready` 后再编辑不重跑分析，只更新前端 Prompt 状态
- 同一步骤只保留一个有效任务，防止重复提交
- 前端轮询间隔建议：分析 2 秒，生成 3 秒

| --- | --- | --- | --- |

### 5.3 需要刻意避免的过度设计

| 不引入的内容 | 原因 |
| --- | --- |
| 独立 Prompt 版本表 | 首版无版本回溯交互，快照存生成任务即可（ADR-6） |
| Redis / 消息队列 / Worker | 首版并发低，数据库轮询足够（ADR-3） |
| 多 Provider 注册中心 | 首版只接一个视觉模型 + 一个 LLM + 一个生图模型 |
| 完整用户认证体系 | 首版不强制登录，匿名即可完成闭环 |
| 独立 Asset 微服务 | 上传逻辑简单，直接在 API Routes 中处理 |
| SSE / WebSocket 实时推送 | 轮询足够，推送增加前后端复杂度 |

## 6. 运行链路

### 6.1 上传与分析

1. 浏览器调用 `POST /api/upload/presign`，获取预签名 URL 和 `assetId`
2. 浏览器使用预签名 URL 直传参考图到对象存储
3. 上传完成后，浏览器调用 `POST /api/analysis`，传入 `assetId`、`fileUrl`、图片元数据
4. API 创建 Asset 记录（type: reference）和 AnalysisTask 记录（status: pending）
5. API 同步调用视觉理解模型，传入图片 URL，获取原始分析文本
6. API 同步调用 LLM，传入原始分析文本和结构化整理 Prompt 模板，获取 VisualRecipe + Prompt + Negative Prompt
7. API 将结构化配方和 Prompt 写入 AnalysisTask（status: completed）
8. 浏览器轮询 `GET /api/analysis/:id`，获取完成状态和结果数据

这条链路的实现原则：

- 上传走预签名 URL 直传，图片二进制不经过 API 层
- 步骤 5-7 在同一次 API 请求中串行完成（非后台异步），因为首版分析耗时目标 <= 30 秒，可以接受长请求
- 如果串行调用总耗时接近超限，优先优化 Prompt 模板压缩 LLM 输出量，不改链路结构
- 分析失败时返回明确错误阶段（vision_failed / llm_failed），前端据此展示不同提示

### 6.2 生成

1. 用户在工作区确认或编辑 Prompt，设置生成参数
2. 浏览器调用 `POST /api/generation`，传入 `analysisTaskId`、`promptText`、`negativePromptText`、生成参数
3. API 创建 GenerationTask 记录（status: pending），将 Prompt 和参数快照存入任务
4. API 异步调用生图模型（生图耗时通常 10-60 秒，不适合在请求内同步等待）
5. 生图完成后，API 将结果图上传到对象存储，创建 Asset 记录（type: generated）
6. API 更新 GenerationTask（status: completed，关联 resultAssetId）
7. 浏览器轮询 `GET /api/generation/:id`，获取完成状态和结果图 URL

这条链路的实现原则：

- 生成任务是真正的异步：POST 创建任务后立即返回 taskId，后续由后台完成调用
- 首版后台异步用 `setTimeout` 或 Next.js API Route 内部 fire-and-forget 实现，不引入队列
- 每次生成记录完整 Prompt 快照，不依赖外部版本引用
- 生成失败时保留 Prompt 和参数，用户可直接重试

## 7. 领域对象与关键契约

### 7.1 核心对象

| 对象 | Source of Truth | Owner | 用途 |
| --- | --- | --- | --- |
| Asset | PostgreSQL `assets` 表 | Upload API / Generation API | 记录参考图和生成图的元数据，实际文件在对象存储 |
| AnalysisTask | PostgreSQL `analysis_tasks` 表 | Analysis API | 承载分析任务状态、结构化视觉配方、初始 Prompt |
| VisualRecipe | `analysis_tasks.recipe` JSON 字段 | Analysis API | 结构化视觉配方，系统核心中间层产物 |
| GenerationTask | PostgreSQL `generation_tasks` 表 | Generation API | 承载生成任务状态、Prompt 快照、参数、结果引用 |

### 7.2 推荐最小 Schema

```typescript
// 资产记录
interface Asset {
  id: string                          // ULID
  type: 'reference' | 'generated'
  fileUrl: string
  thumbnailUrl: string | null
  width: number
  height: number
  mimeType: string                    // image/jpeg, image/png, image/webp
  createdAt: string                   // ISO 8601
}

// 结构化视觉配方（扁平结构，嵌套 1 层）
interface VisualRecipe {
  imageSummary: string
  subject: string
  scene: string
  composition: string
  cameraLanguage: string
  lighting: string
  color: string
  texture: string
  styleTags: string[]
  mood: string
  visualKeywords: string[]
  mustKeep: string[]
  replaceable: string[]
}

// 分析任务
interface AnalysisTask {
  id: string                          // ULID
  sourceAssetId: string
  status: 'pending' | 'processing' | 'completed' | 'failed'
  recipe: VisualRecipe | null         // 分析完成后填充
  promptText: string | null           // 系统生成的初始 Prompt
  negativePromptText: string | null
  rawResponse: string | null          // 视觉模型原始返回，用于排障
  errorMessage: string | null
  errorStage: 'vision' | 'llm' | null // 失败阶段
  createdAt: string
  updatedAt: string
}

// 生成参数
interface GenerationParams {
  aspectRatio: string                 // 如 "1:1", "16:9", "4:3"
  quality: string                     // 如 "standard", "hd"
}

// 生成任务
interface GenerationTask {
  id: string                          // ULID
  analysisTaskId: string
  status: 'pending' | 'processing' | 'completed' | 'failed'
  promptSnapshot: string              // 生成时使用的完整 Prompt
  negativePromptSnapshot: string
  params: GenerationParams
  modelName: string
  resultAssetId: string | null        // 生成完成后关联
  errorMessage: string | null
  createdAt: string
  updatedAt: string
}
```

### 7.3 API 边界

| 接口 | 方法 | 用途 | 说明 |
| --- | --- | --- | --- |
| `/api/upload/presign` | POST | 获取预签名上传 URL | 入参：fileName, mimeType；返回：presignedUrl, fileUrl, assetId |
| `/api/analysis` | POST | 创建分析任务并触发分析 | 入参：assetId, fileUrl, width, height, mimeType；同步完成分析后返回结果 |
| `/api/analysis/:id` | GET | 查询分析任务状态和结果 | 返回 AnalysisTask 完整数据，含 recipe 和 Prompt |
| `/api/generation` | POST | 创建生成任务 | 入参：analysisTaskId, promptText, negativePromptText, params；异步执行，立即返回 taskId |
| `/api/generation/:id` | GET | 查询生成任务状态和结果 | 返回 GenerationTask 完整数据，含 resultAssetId 和对应 fileUrl |

共 5 个端点，每个对应首版用户流程中的具体交互。

### 7.4 状态流转

分析任务状态：

```
pending → processing → completed
pending → processing → failed
failed →（用户重新上传触发新任务，不复用失败任务）
```

生成任务状态：

```
pending → processing → completed
pending → processing → failed
failed →（用户点击重试创建新任务，不复用失败任务）
```

规则：任务一旦进入终态（completed / failed）不可变更。重试通过创建新任务实现。

### 7.5 数据边界

| 存储层 | 存储内容 | 职责边界 |
| --- | --- | --- |
| 对象存储（R2） | 参考图原图、生成结果图 | 只存文件，不存业务状态 |
| PostgreSQL | Asset 元数据、AnalysisTask（含 VisualRecipe JSON）、GenerationTask（含 Prompt 快照） | 业务数据的 source of truth |
| 浏览器内存 | 当前工作区状态、用户编辑中的 Prompt | 会话级临时状态，刷新即丢失（首版可接受） |

### 7.6 命名与标识规则

- **ID 策略**：所有实体统一使用 ULID，不使用类型前缀
- **JSON 命名**：camelCase（前端和 API 统一）
- **数据库命名**：snake_case
- **术语映射**：

| 业务概念 | 代码 / API 术语 | 说明 |
| --- | --- | --- |
| 结构化视觉配方 | `recipe` / `VisualRecipe` | 不使用 `config`、`profile`、`style` |
| Prompt | `promptText` | 不缩写为 `prompt`，避免与 LLM prompt 概念冲突 |
| Negative Prompt | `negativePromptText` | 统一全称 |
| 参考图 | `Asset(type: reference)` | 不单独建 ReferenceImage 类型 |
| 生成图 | `Asset(type: generated)` | 不单独建 GeneratedImage 类型 |
| 必保留项 | `mustKeep` | 不使用 `required`、`locked` |
| 可替换项 | `replaceable` | 不使用 `optional`、`swappable` |

## 8. 非功能需求、风险与运行策略

### 8.1 性能与吞吐量目标

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 上传耗时 | <= 5 秒（10MB 以内） | 预签名 URL 直传，不经过 API |
| 分析耗时 | <= 30 秒 | 两阶段串行，视觉模型 + LLM |
| 生成耗时 | <= 60 秒 | 取决于生图模型 |
| 端到端耗时（上传到首张结果图） | <= 90 秒 | 分析 + 生成合计 |
| 轮询 QPS | <= 10 QPS / 用户 | 分析 2 秒、生成 3 秒间隔 |
| 首版预期并发 | <= 20 个同时在线用户 | 灰度阶段 |

### 8.2 可靠性、错误处理与降级策略

基础错误处理：

- 上传失败：前端提示重新上传，不创建后续任务
- 分析失败：记录 `errorStage`（vision / llm），展示对应提示和重试入口，保留原图
- 生成失败：保留 Prompt 和参数，展示失败原因，允许重试
- 超时处理：分析超时 60 秒、生成超时 120 秒，超时按失败处理

降级策略（按用户体验影响从小到大）：

| 级别 | 触发条件 | 系统行为 | 用户可见影响 |
| --- | --- | --- | --- |
| L1 | 生图模型响应慢 | 延长轮询间隔，展示排队提示 | 等待时间变长 |
| L2 | 生图模型不可用 | 关闭生成入口，保留分析和编辑能力 | 无法生成，但可查看和编辑配方 |
| L3 | LLM 不可用 | 分析链路降级为仅返回视觉模型原始结果，不做结构化整理 | 配方质量下降，Prompt 需手动编写 |
| L4 | 视觉模型不可用 | 暂停分析入口，提示稍后重试 | 无法分析新图，但已有结果可查看 |
| L5 | 数据库不可用 | 整页维护提示 | 产品完全不可用 |

### 8.3 安全与反滥用策略

| 项目 | 首版策略 |
| --- | --- |
| API Key 管理 | 所有模型 API Key 仅服务端持有，通过环境变量注入，不在客户端暴露 |
| System Prompt 隔离 | 视觉分析和结构化整理的 system prompt 与用户输入严格分离，用户编辑内容仅进入 user message |
| 内容安全 | 上传阶段校验文件类型和大小（JPG/PNG/WebP，<= 10MB）；生图 Prompt 依赖模型自带的安全过滤 |
| Rate Limit | 按 IP 限流：上传 10 次/小时，分析 10 次/小时，生成 20 次/小时 |
| Prompt 注入防护 | 用户编辑的 Prompt 仅用于生图模型调用，不回流到视觉分析或 LLM 结构化链路 |

### 8.4 成本控制预期

| 服务 | 预估单次成本 | 首版控制策略 |
| --- | --- | --- |
| 视觉理解模型 | $0.01 - $0.05 / 次 | 按 IP 限流；单次分析只调用一次 |
| LLM 结构化整理 | $0.01 - $0.03 / 次 | 控制输出 token 上限；Prompt 模板精简 |
| 生图模型 | $0.02 - $0.10 / 次 | 按 IP 限流；首版不支持批量生成 |
| 对象存储 | < $0.01 / GB·月 | 首版数据量极小，暂不设清理策略 |

首版日预算上限建议 $50，超限时关闭新任务创建并提示稍后重试。

### 8.5 可观测性

最小可观测方案：

- **应用日志**：每个 API 请求记录 taskId、耗时、状态、错误信息，使用结构化 JSON 格式输出
- **前端埋点**：接入 GA4，覆盖需求文档定义的最小埋点集（workspace_entered、analysis_result、generate_clicked、generation_result、feedback_submitted）
- **告警**：首版通过日志监控。当分析或生成失败率连续 1 小时超过 10% 时触发告警（具体告警通道视部署环境决定）
- **排障标识**：每个任务携带 ULID，可通过 taskId 在日志和数据库中完整追溯链路

### 8.6 主要风险

| 风险 | 影响 | 缓解方式 |
| --- | --- | --- |
| 分析结果结构化不稳定 | 前端展示异常，Prompt 质量不可控 | LLM 调用使用 JSON mode 或 structured output；前端对缺失字段做兜底展示 |
| 生图结果偏离参考风格 | 用户对产品价值判断负面 | 产品层面明确"再创作而非复刻"；技术层面优化 Prompt 模板和参数 |
| 外部模型服务中断 | 主链路阻断 | 降级策略分级处理（8.2）；生成入口可快速关闭 |
| 成本失控 | 预算超支 | 按 IP 限流 + 日预算上限 + 超限自动暂停 |
| 用户上传敏感 / 侵权内容 | 合规风险 | 文件类型校验 + 依赖生图模型安全过滤；使用条款声明用户对上传内容负责 |

## 10. 架构结论

首版架构围绕 **Reference → Recipe → Render** 核心闭环设计，关键判断如下：

1. **结构化视觉配方是系统核心**：数据模型围绕 VisualRecipe 设计，不围绕一段 Prompt 文本。配方是 source of truth，Prompt 是派生产物。

2. **两阶段 AI 链路保证职责清晰**：视觉模型负责看图，LLM 负责结构化整理和 Prompt 生成。两者解耦，便于独立优化和替换。

3. **最小技术复杂度**：不引入消息队列、WebSocket、多 Provider 抽象、Prompt 版本表、完整账号体系。首版用数据库轮询、预签名 URL 直传、ULID 标识、Next.js 单体完成所有需求。

4. **降级优先于扩展**：外部模型不可用时分级降级，始终保留用户已完成的数据。生成入口可快速关闭，分析能力尽量保持可用。

5. **演进路径明确**：当前架构不阻碍后续引入消息队列、多模型适配、用户体系和资产管理。每个 ADR 都标注了演进余地，避免首版为未来假设提前付出成本。

首版成功不以"功能多少"判断，而以"闭环是否成立"判断——用户能否从参考图出发，通过结构化配方，稳定生成同风格新图。
