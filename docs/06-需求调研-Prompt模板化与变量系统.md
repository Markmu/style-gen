# 06 需求调研：Prompt 模板化与变量系统

## 0. 文档说明

**产出时间**：2026-04-07
**研究方式**：苏格拉底式对话 + 竞品深度拆解（5 个竞品）+ 可行性评估
**后续动作**：交由 prd-gen 生成正式 PRD
**状态**：待用户审阅补充

## 1. 需求概述

- **一句话描述**：让分析后的 prompt 可保存为参数化模板，支持变量插入与批量复用
- **核心问题**：当前 workspace 完成视觉分析后，生成的 prompt 是一次性纯文本——用户无法将「风格模式」保存下来复用。想用同一风格生成不同主体时，必须重新分析或手动复制粘贴编辑，体验断裂
- **目标用户**：需要用同一视觉风格批量创作不同内容的设计师、创作者
- **触发场景**：
  1. 用户完成一张参考图的分析，对生成的 prompt 满意，希望保存为可复用的模板
  2. 用户已有风格模板，想快速填入不同主体/场景生成新图
  3. 用户在编辑 prompt 时发现某些部分是「可替换的」，想标记为变量
- **成功标准**：
  - 用户能从分析结果一键保存为命名模板
  - 模板中的变量可在任意位置插入和编辑
  - 加载模板后能通过向导式 UI 填写变量值并生成

## 2. 竞品分析

### 2.1 竞品概览

| 竞品 | 产品定位 | 相关功能 | 核心优势 | 主要不足 |
|------|----------|----------|----------|----------|
| **ComfyUI** | 节点式 AI 工作流引擎 | 原始文本 `{}` 变量插值 + Primitive 节点 | 极致灵活，工作流可组合 | 无结构化模板 UI；纯文本编辑变量对非技术用户不友好 |
| **Fooocus** | 自动化 SD WebUI | 风格全量预设（py 文件定义） | 开箱即用，零配置体验 | 预设不可部分覆盖；无法只替换主体保留风格 |
| **Leonardo.ai** | 商用 AI 图像生成平台 | **Blueprints 向导式变量 UI** — 可视化表单字段 | 最佳 UX：用户无需记语法，表单直观填值 | 不支持从参考图自动提取模板；需手动创建 |
| **Civitai** | 模型社区 + 图像生成 | Prompt 模板复制（纯文本） | 社区生态丰富，模板资源多 | 无变量能力；只能整段复制，无法参数化 |
| **Midjourney** | 高质量艺术图像生成 | `/prefer` 参数预设 + `--sref` 风格引用 | 风格引用模式简洁优雅 | 参数预设为静态字符串，无变量/模板概念 |

### 2.3 核心路径拆解

**Leonardo.ai — Blueprints**

```text
步骤1: 用户进入 Blueprints 页面，浏览社区/官方模板
步骤2: 选择一个模板（如"产品摄影风格"）
步骤3: 系统展示可视化表单，每个变量对应一个输入框
步骤4: 用户填写各字段值 → 点击 Generate → 生成 4 张变体
```

关键体验点：**变量即表单字段**——用户完全不需要理解 prompt 语法，填表即可。这是目前业界最佳实践。

**ComfyUI — 工作流变量**

```text
步骤1: 在节点编辑器中添加 Primitive 节点（文本/数字/下拉）
步骤2: 将其他节点的输入口连接到 Primitive 节点的输出口
步骤3: 点击 Queue Prompt 时弹出变量填值窗口
步骤4: 填写后提交，工作流使用填入的值执行
```

关键体验点：**变量作为一等公民节点**——灵活但学习曲线陡峭。

**Midjourney — /prefer 风格预设**

```text
步骤1: 用户输入 /prefer option set <param> <value>
步骤2: 系统保存该参数为默认值
步骤3: 后续 /imagine 自动应用已设参数
```

关键体验点：**极简但受限**——只能设固定值，无变量概念。

### 2.4 差异化洞察

**可借鉴**：
- **Leonardo.ai Blueprints 的向导式变量 UI** — 用户不需要记 `{{var}}` 语法，通过表单字段直观填值，降低认知负担
- **ComfyUI 的「槽位」概念** — 将 prompt 中可替换的部分抽象为独立变量，技术上清晰

**应避免**：
- **Fooocus 式全量预设** — 一套 preset 覆盖所有参数，用户无法只改主体保留风格 → 我们应支持**局部变量**
- **ComfyUI 式原始文本框中手写 `{variable}`** — 对非技术用户不友好 → 需要**可视化变量插入**
- **Civitai 式无结构化整段复制** — 只能复制不能复用模式 → 必须有**变量语义**

**差异化机会**：
> **没有任何竞品实现「从参考图自动提取 → 结构化 prompt → 参数化模板」的完整闭环。** style-gen 独有的 Reference → Recipe → Render 价值链，加上模板化能力后将形成竞争壁垒。

## 3. 可行性评估

| 维度 | 评级 | 说明 |
|------|------|------|
| 必要性 | **高** | 当前 prompt 一次性使用，无法复用风格模式。同一风格换主体必须重新分析或手动复制粘贴，核心工作流在此处断裂 |
| 紧迫性 | **中高** | 这是 Reference → Recipe → Render 自然延伸，不做则用户在「编辑 prompt」步流失率会高 |
| 技术可行性 | **高** | 技术栈完全支撑：Drizzle 新增 templates 表 + API route + 前端组件扩展。无不确定技术风险 |
| 资源投入 | **中（3-5 天）** | DB schema + repository + CRUD API + 独立模板面板组件（变量高亮/插入/向导填值）+ workspace 三列布局集成 |

**主要风险**：

1. **变量语法解析与渲染复杂度** — 在编辑器中实现 `{{var}}` 高亮和内联编辑有一定前端复杂度
   - 缓解思路：MVP 采用「标记显示 + 弹窗/侧栏编辑」方案，避免自研富文本编辑器；或基于 contentEditable 方案
2. **模板面板与现有 workspace 三列布局的集成** — 当前已是三列（图片 | 风格拆解 | Prompt+输出），新增第四区域需重新考虑布局
   - 缓解思路：模板面板采用抽屉/弹窗模式，不占用主布局空间；或将模板选择嵌入 PromptEditor 区域内
3. **模板 JSONB schema 的扩展性设计** — 变量定义需支持未来增强（类型、校验规则、默认值选项等）
   - 缓解思路：JSONB 存储变量数组，schema 版本化，预留扩展字段

**评估结论**：**建议推进**，按 P0/P1/P2 分阶段交付

## 4. 初步范围建议

**P0（MVP 必须）**：

- `templates` 数据表（name, promptTemplate, negativePromptTemplate, variables JSONB, userId, sourceAnalysisTaskId）
- Template Repository（CRUD）
- 模板 CRUD API（`/api/templates`：列表、创建、更新、删除）
- **独立的 TemplatePanel 组件**（组件自身能力：模板列表、编辑器、变量管理；workspace 集成布局延后）
- 从当前分析结果「保存为模板」入口
- 变量插入交互：工具栏按钮 → 插入 `{{variableName}}`，支持自定义变量名和默认值
- 模板加载到编辑器的交互（选中模板 → 填充 prompt 文本）

**P1（建议做）**：

- 变量向导填值 UI：加载模板后自动识别 `{{var}}`，展示表单让用户填写变量值
- 模板列表管理：重命名、复制、删除确认
- Negative Prompt 的模板化支持（与 Positive Prompt 对称）

**P2（可以后做）**：

- 预设模板库（系统内置 3-5 个通用风格模板）
- 模板分类/标签
- 模板导入/导出
- 模板分享/社区
- 批量生成（一次填值 → 多组变体）

**明确不做（MVP 阶段）**：

- 预设模板库（用户明确表示 MVP 先不做，聚焦自定义模板）
- 模板分享/社区功能（涉及用户系统和权限，范围过大）
- 与 ComfyUI 工作流的互导入（技术方向差异大）

| # | 决策问题 | 初步倾向 | 需要补充的信息 |

| 1 | ~~模板面板的呈现形式？弹窗 / 侧边抽屉 / 内嵌区域~~ | **延后**：workspace 引入模板组件后的布局与交互待后续独立分析 | 需先完成模板核心能力（CRUD + 变量），再基于实际组件形态做布局决策 |
| 2 | 变量语法的最终格式？`{{var}}` / `${var}` / 自定义标记 | `{{var}}`（与行业惯例一致） | 是否需要支持嵌套或表达式 |
| 3 | 变量的元信息范围？仅 name+defaultValue / 含 type/hint/options | MVP 仅 name + defaultValue | 后续是否需要变量类型约束 |
| 4 | 模板是否关联来源分析任务？保存时记录 sourceAnalysisTaskId | **是**，方便追溯模板来源 | 是否需要在模板详情中展示来源图的缩略图 |

> **注**：决策 #1（模板面板在 workspace 中的布局与交互方式）已明确**延后至后续独立分析**。本次需求调研聚焦模板核心能力（数据层 + CRUD + 变量机制），不预设集成方案。

## 6. 研究过程记录

### 关键问答摘要

> 供 prd-gen 编写 PRD 时参考上下文

**Q: 你观察到什么具体现象让你觉得需要做「提示词模板化」？**
A: 预设模板 + 自定义两者都需要。不只是自己遇到的痛点，而是产品自然演进的方向。

**Q: 变量主要解决什么问题？**
A: 主体/场景等可替换部分的变量化。核心场景是同一风格模板换不同内容批量生成。

**Q: MVP 最小可行版本的范围？**
A: 先看竞品再定范围。（已完成竞品分析）

**Q: 基于竞品分析，倾向哪种变量交互方式？**
A: **两者结合** —— 编辑器内联变量高亮 + 编辑，同时提供向导式表单填值 UI。

**Q: 预设模板是否在 MVP 包含？**
A: **MVP 不含预设，先做自定义模板**。聚焦从分析结果创建和管理模板的核心链路。

**Q: 模板存储方案？**
A: **数据库持久化**（非 localStorage）。需要新建 templates 表存 PostgreSQL，支持跨设备同步。

**Q: 文档审阅后的补充说明？**
A: **workspace 引入模板组件后的布局与交互待后续分析**——本次聚焦模板核心能力（数据层 + CRUD + 变量机制），不预设集成布局方案。决策点 #1（面板呈现形式）标记为延后。
