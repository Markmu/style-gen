# 01-0 需求设计：参考图风格提取与再创作

## 0. 文档说明

本文件是项目的 0 号总文档，用于统一需求、竞品、用户、体验和技术方案，作为后续 PRD、原型和开发的基础。

产品核心目标：

**帮助用户从参考图中提炼可迁移的视觉语言，生成可编辑 Prompt，并据此产出同风格但非同图的新作品。**

---

# 第一部分 需求分析与确认（含竞品分析）

## 1.1 项目背景

用户希望构建一个 Web 应用，支持以下核心能力：

- 上传一张参考图
- 使用视觉理解模型分析图片
- 提取该图片的风格、构图、光影、色彩、材质等视觉语言
- 生成可编辑 Prompt
- 基于 Prompt 调用生图模型生成同风格新图

这个产品的目标不是“复刻原图”，而是：

**参考图 -> 视觉配方 -> Prompt -> 同风格再创作**

---

## 1.2 核心问题定义

当前用户在“参考图驱动创作”上通常会遇到几个问题：

- 看得懂参考图好看，但说不清为什么好看
- 不擅长把图片转成有效 Prompt
- 普通 image-to-prompt 工具输出不稳定，也不够可编辑
- 参考图生成结果往往依赖单次运气，难以沉淀复用

因此本产品要解决的不是单点“图转 Prompt”，而是：

- 如何把图片转成结构化视觉语言
- 如何让分析结果可解释、可编辑、可复用
- 如何支持用户基于同一种风格持续再创作

### 如果不做这个功能

- 用户仍然需要在手写 Prompt、反推 Prompt 工具和不同生图产品之间来回切换，试错成本高且结果不稳定
- “看得出好看但说不清怎么复用”的问题仍然存在，参考图价值无法沉淀成可持续复用的视觉资产
- 轻量用户会停留在“想试但不会写 Prompt”的阶段，专业用户会转向更成熟的参考图工作流产品
- 产品层面会失去一个差异化明确的 AI 创作入口，容易退回到同质化的图转 Prompt 工具竞争

### 首版成功标准

首版成功标准不是证明“平台化能力已经成熟”，而是验证以下闭环是否成立：

**参考图 -> 结构化分析 -> 可编辑 Prompt -> 同风格再创作**

建议首版以以下指标作为对齐口径：

- `分析完成率 >= 95%`：上传或选择示例图后，绝大多数任务都能稳定返回结构化分析结果
- `生成完成率 >= 95%`：进入工作区并发起生成的任务中，绝大多数任务都能成功返回结果图
- `首轮闭环完成率 >= 35%`：首次进入工作区的用户中，至少有一部分能完成“分析 -> 编辑/确认 -> 生成 -> 查看结果”
- `Prompt 直接采纳或轻编辑后使用率 >= 60%`：说明分析结果不是展示信息，而是真正可用于生成
- `从上传到首张结果图的中位耗时 <= 90 秒`：用户能在可接受时间内完成一次完整体验
- `分析结果主观有效性 >= 70%`：用户反馈分析结果“有帮助”或“较准确”

### 目标与价值判断

#### 功能目标

- 验证“参考图 -> 结构化分析 -> 可编辑 Prompt -> 同风格再创作”这条核心闭环是否真实成立
- 降低首次使用门槛，让不会写 Prompt 的用户也能快速进入创作
- 建立产品的首个差异化能力，而不是落入普通图转 Prompt 工具竞争

#### 用户价值

- 更快：用户不需要从零拆图、从零写 Prompt，可以直接从参考图开始
- 更省：减少在多个工具之间来回切换和反复试错的成本
- 更准：把风格、构图、光影、材质等视觉要素拆成结构化信息，降低黑盒感
- 更可控：用户可以编辑 Prompt、保留风格、替换主体，而不是依赖单次运气
- 更可复用：一次分析结果可以沉淀为后续持续使用的视觉配方

#### 业务价值

- 提升首页到工作区的转化效率，验证用户是否愿意为“参考图驱动创作”进入深度体验
- 提升首轮生成激活率，判断结构化分析是否能真实驱动后续生成行为
- 建立产品差异化心智，避免与普通 `image-to-prompt` 工具陷入同质竞争
- 为后续历史记录、模板库、多模型适配和付费能力提供可复用的中间层基础

#### 优先级判断

- 这是首版最应该优先验证的能力，因为它同时连接用户真实痛点、产品差异化和后续扩展空间
- 如果不先验证这个闭环，后续做模板库、多模型、品牌风格包等能力都会缺少可靠基础
- 市场已经验证“参考图驱动创作”是成立需求，但“结构化视觉配方”仍有明显空白，因此现在做优先级高于平台化扩展

#### ROI 粗判断

- 投入：中等。主要投入集中在工作区体验、分析链路、Prompt 生成链路和单模型生成闭环
- 收益：中高。可以直接验证差异化能力、转化效率和后续资产化方向是否成立
- 判断：首版适合用 MVP 方式快速验证，不适合一开始投入过重的平台化建设

#### 推进结论

- 结论：建议推进
- 推进方式：先做轻量首版，优先验证结构化分析结果是否能稳定转化为可用生成结果
- 本期不追求：多模型深度适配、复杂协作体系、重资产管理后台

## 1.3 产品定位确认

不建议将产品定位为：

**Image to Prompt Generator**

更适合的定位是：

- 视觉风格提取与再创作工作台
- 把参考图变成可复用视觉配方的 AI 应用
- Reference -> Recipe -> Render

定位理由：

- 避免落入单点小工具心智
- 强调结构化解释与资产沉淀
- 为后续多模型适配和风格资产化预留空间

## 1.4 产品边界确认

### 首版要解决的问题

- 用户能否从参考图中拿到可信的结构化分析结果
- 用户能否直接基于分析结果生成同风格新图
- 用户能否在工作区继续编辑 Prompt 并迭代结果

### 首版暂不重点解决的问题

- 多模型深度适配
- 社区与模板生态
- 团队协作与权限体系
- LoRA 训练
- 企业级品牌资产管理

## 1.8 竞品分析

### 1.8.1 市场格局

围绕“参考图 -> 风格理解 -> Prompt 生成 -> 再生成”这条链路，现有竞品大致可归为四类：

| 类型 | 代表产品 | 主要能力 | 与本产品关系 | 关键判断 |
| --- | --- | --- | --- | --- |
| 直接型：Image to Prompt / Reverse Prompt | Krea、Picsart、Promptsera | 上传图后生成 Prompt，可继续进入生成 | 最接近直接竞品 | 强在入口清晰，但通常停留在 Prompt 文本层 |
| 参考图驱动型：Style / Composition Reference | Midjourney、Adobe Firefly、Leonardo | 用参考图控制风格、构图、角色或对象并直接生成 | 覆盖下游主需求 | 强在生成控制，不强在结构化解释 |
| 视觉优先创作型：图片代替 Prompt | Google Whisk | 以图片代替文字 Prompt 做快速探索 | 会分流轻量用户 | 强在低门槛，不强在专业分析 |
| 提示词生态型：模板 / 社区 / 搜索 | PromptHero、OpenArt | 搜索相似 Prompt、模板、工作流 | 间接分流 | 抢走“找灵感/找现成 Prompt”需求 |

| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Krea | 直接型 | 上传图后生成 generation-ready Prompt，并进入创作流程 | 强 | 强 | 强 | 中 | 弱 | 高 |

| Adobe Firefly | 参考图驱动型 | 面向设计工作流的风格参考、构图参考与品牌复用 | 弱/间接 | 很强 | 很强 | 中 | 强 | 高 |
| Google Whisk | 视觉优先创作型 | 用图片直接充当 Prompt 进行快速视觉探索 | 间接 | 强 | 强 | 弱 | 弱 | 中高 |
| Leonardo | 参考图驱动 / 平台型 | 多模型生成基础设施与高级参考图控制 | 弱/间接 | 强 | 强 | 弱 | 中 | 中 |

### 1.8.3 竞品对比表

| 产品 | 主要优势 | 主要短板 | 最值得借鉴 | 需要刻意区分 |
| --- | --- | --- | --- | --- |

### 1.8.4 竞品分析结论

#### 表格之外的关键判断

已被验证的需求：

- 用户确实有“参考图驱动创作”的强需求
- 用户不愿花太多时间学习 Prompt 工程
- “图 -> 生成”闭环已经被市场教育

仍存在的空白：

- 缺少稳定、好用的结构化中间层
- 缺少把分析结果沉淀为视觉资产的产品
- 缺少面向多模型的统一 Prompt Renderer 心智

本产品的差异化方向：

- 不只输出一段 Prompt，而是输出结构化视觉配方
- 支持“保留风格、替换主体”
- 强调分析结果可编辑、可复用、可沉淀

## 1.9 方案比较与取舍

### 1.9.1 产品方案比较

围绕“参考图驱动创作”这件事，首版至少存在三种可行产品方案：

| 方案 | 描述 | 用户体验 | 开发成本 | 风险 | 可扩展性 | 上线速度 | 数据验证能力 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 方案 A：纯 `image-to-prompt` 工具 | 上传图片后直接输出一段 Prompt，用户自行再去生成 | 上手快，但容易回到黑盒体验 | 低 | 容易同质化，结果不稳定 | 弱 | 快 | 中 |
| 方案 B：结构化视觉配方工作台 | 先分析视觉语言，再输出可编辑 Prompt，并在同一工作区完成生成 | 理解成本略高，但可解释、可编辑、可沉淀 | 中 | 需要把分析结果做得足够可信 | 强 | 中 | 强 |
| 方案 C：参考图直接生成 + 轻量解释 | 上传图片后直接生成结果，只给少量解释信息 | 体验最轻，但专业用户难以控制 | 中 | 容易把失败归因变成黑盒 | 中 | 中 | 弱 |

取舍判断：

- 方案 A 的优势是快，但难以建立差异化，最终会回到 Prompt 文本工具竞争
- 方案 C 的优势是低门槛，但无法支撑“可编辑、可复用”的核心定位
- 方案 B 更符合当前产品目标，虽然首版实现复杂度更高，但最能验证差异化价值

最终选择：

- **选择方案 B：结构化视觉配方工作台**
- 原因：它最符合“Reference -> Recipe -> Render”的核心定位，也最利于后续沉淀视觉资产

### 1.9.2 页面方案比较

页面结构至少有三种设计思路：

| 方案 | 描述 | 优点 | 缺点 | 最终判断 |
| --- | --- | --- | --- | --- |
| 方案 A：单页流 | 首页、上传、分析、生成全部放在一个页面 | 路径最短，开发看似简单 | 信息密度高，首页和工作区职责混乱 | 不选 |
| 方案 B：首页 + 工作区双页流 | 首页负责理解价值，工作区负责分析、编辑和生成 | 职责清晰，符合首次体验节奏 | 页面跳转增加一步 | 选用 |
| 方案 C：首页长页 + 内嵌工作台 | 首页下半部分直接嵌入工作区能力 | 兼顾展示和体验 | 页面复杂，状态切换容易混乱 | 不选 |

最终选择：

- **选择方案 B：首页 + 工作区双页流**
- 原因：首页的目标是转化，工作区的目标是完成闭环，两者拆开后更容易建立清晰心智

### 1.9.3 首版实现方案比较

首版技术和产品边界也存在三种实现思路：

| 方案 | 描述 | 优点 | 缺点 | 最终判断 |
| --- | --- | --- | --- | --- |
| 方案 A：单模型闭环 | 只接 1 个分析链路和 1 个生图模型，先跑通闭环 | 实现最稳、上线最快 | 扩展性一般 | 部分采纳 |
| 方案 B：多模型抽象层 | 首版就做统一 Provider 抽象，支持多模型切换 | 架构上更完整 | 首版复杂度高，验证效率低 | 不选 |
| 方案 C：单模型闭环 + 结构化中间层 | 首版只接 1 个生图模型，但先把结构化视觉配方 schema 建起来 | 兼顾验证速度与未来扩展 | 需要前期想清数据结构 | 选用 |

最终选择：

- **选择方案 C：单模型闭环 + 结构化中间层**
- 原因：它兼顾了首版验证效率和后续多模型、多资产形态扩展能力

### 1.9.4 取舍结论

当前文档中的关键决策，最终收敛如下：

- 产品形态：选择“结构化视觉配方工作台”，不做纯图转 Prompt 工具
- 页面结构：选择“首页 + 工作区”双页流，不做大而全单页流
- 首版实现：选择“单模型生成闭环 + 结构化中间层”，不做首版多模型平台

这些取舍共同服务于一个目标：

**先验证差异化闭环是否成立，再决定是否进入更重的平台化建设。**

# 第二部分 用户旅程和用户故事

## 2.1 核心用户类型

### 独立创作者

诉求：

- 快速拿到可用 Prompt
- 看懂图像风格
- 低门槛生成同风格新图

### 设计师 / 视觉从业者

诉求：

- 结构化拆解视觉语言
- 进行可控编辑
- 稳定生成接近参考风格的结果

### 轻量探索型用户

诉求：

- 快速试用
- 不想写 Prompt
- 想先看示例再决定是否深入使用

---

## 2.2 核心用户旅程

```text
认知产品
  -> 进入首页
  -> 理解产品价值
  -> 上传参考图 / 选择示例图
  -> 进入工作区
  -> 等待自动分析
  -> 查看结构化分析结果
  -> 编辑 Prompt / 调整配方
  -> 发起生成
  -> 查看结果并对比
  -> 决定继续迭代或结束
```

---

## 2.3 主旅程拆解

### 阶段 1：进入首页

用户目标：

- 快速理解产品能做什么
- 判断是否值得尝试

关键设计点：

- 首页必须清晰表达“结构化分析 + 同风格再创作”
- 示例展示必须覆盖“原图 -> 分析 -> 结果”

### 阶段 2：进入工作区并开始分析

用户目标：

- 让系统快速理解参考图

关键设计点：

- 分析中过程要可视化
- 最少展示内容识别、风格拆解、Prompt 生成三个阶段

### 阶段 3：查看分析结果

用户目标：

- 判断分析是否准确
- 理解哪些元素值得保留

关键设计点：

- 区分内容和风格
- 增加“必保留项 / 可替换项”

### 阶段 4：编辑并生成

用户目标：

- 把分析结果改造成自己想要的输出

关键设计点：

- Prompt 编辑入口要明确
- 风格强度与主体替换要靠近生成按钮

### 阶段 5：查看结果并继续迭代

用户目标：

- 判断结果是否符合预期
- 决定继续迭代还是结束

关键设计点：

- 对比视图要清晰
- 支持从结果继续再生成

---

## 2.4 次旅程

### 次旅程 A：示例图快速体验

路径：

```text
首页 -> 点击示例图 -> 进入工作区 -> 查看已完成分析 -> 点击生成 -> 查看结果
```

价值：

- 降低首次使用门槛
- 提高首页转化率

### 次旅程 B：保留风格，替换主体

路径：

```text
上传参考图
  -> 查看分析结果
  -> 理解必保留项 / 可替换项
  -> 输入新主体
  -> 调整风格强度
  -> 生成结果
  -> 对比并继续优化
```

价值：

- 体现产品和普通 image-to-prompt 工具的差异
- 明确“不是复刻原图，而是风格迁移”

---

## 2.5 用户场景边界与异常处理

### 2.5.1 主流程成立条件

用户主流程成立，需要同时满足以下前提：

- 用户已经理解产品不是“复刻原图”，而是“提炼风格后再创作”
- 用户有一张可用于分析的参考图，或愿意先使用示例图快速体验
- 用户愿意接受“先分析，再编辑，再生成”的工作流，而不是一步黑盒出图
- 系统可以正常调用分析链路和生成链路，至少能完成一次闭环体验

首版默认应优先保证“先体验，再决定是否深入使用”：

- 首次体验不应被登录流程阻断
- 用户应先完成上传、分析、查看结果，再决定是否登录或保存
- 保存长期历史、沉淀个人资产、跨设备同步不作为首版主流程前置条件

### 2.5.2 主流程与关键分支

#### 主流程：上传参考图并完成首次再创作

```text
进入首页
  -> 上传参考图
  -> 进入工作区
  -> 系统自动分析
  -> 查看结构化结果
  -> 直接生成或轻量编辑后生成
  -> 查看结果与对比
  -> 结束或继续迭代
```

这个流程对应首版最重要的验证目标：

- 用户能否看懂分析结果
- 用户能否愿意继续生成
- 生成结果能否支撑继续迭代

#### 分支流程 A：示例图快速体验

- 适用对象：还没有准备素材，或者还不确定产品效果的用户
- 核心目标：缩短首次理解时间，快速验证产品价值
- 成立条件：系统内置示例图和已完成分析结果可直接复用

#### 分支流程 B：保留风格，替换主体

- 适用对象：认可原图风格，但不想保留原图内容的用户
- 核心目标：体现本产品与普通图转 Prompt 工具的差异
- 成立条件：分析结果中必须明确哪些元素建议保留，哪些元素允许替换

#### 分支流程 C：分析正确，用户直接生成

- 适用对象：对结构化结果认可度高，希望快速拿结果的用户
- 核心目标：验证分析结果是否足够可信，能减少不必要编辑步骤

#### 分支流程 D：分析不完全准确，用户编辑后再生成

- 适用对象：希望修正风格、构图、主体描述或提示词细节的用户
- 核心目标：验证“分析结果可编辑”是否真的提高可控性，而不是增加负担

### 2.5.3 异常与边界矩阵

| 场景 | 触发条件 | 系统处理 | 用户可继续动作 |
| --- | --- | --- | --- |
| 未上传图片 | 用户直接进入工作区但没有可分析素材 | 不进入分析阶段，明确提示上传参考图或使用示例图 | 上传图片 / 选择示例图 |
| 图片不可用 | 图片损坏、无法解析、内容不完整 | 上传阶段即提示失败原因，不进入后续链路 | 更换图片重新上传 |
| 上传中断 | 网络波动、页面关闭、上传失败 | 明确提示上传失败，不创建分析任务 | 重新上传 |
| 分析失败 | 视觉模型报错、超时、结果结构不完整 | 页面保留原图，显示失败阶段和重试入口 | 重新分析 / 更换图片 |
| 分析质量不佳 | 用户认为主体、风格或构图判断不准确 | 保留结构化结果和 Prompt 编辑入口，不强制用户重传 | 编辑字段 / 编辑 Prompt / 更换图片 |
| 生成失败 | 生图模型异常、任务超时、无结果返回 | 保留当前 Prompt、参数和分析结果，提示失败原因 | 重试生成 / 调整 Prompt / 更换模型参数 |
| 用户中途退出 | 刷新页面、关闭页面、返回首页 | 若任务仍在执行，重新进入后优先恢复最近任务状态；若无法恢复，则至少保留最近稳定状态 | 继续查看结果 / 重试当前步骤 |
| 用户重复提交 | 连续点击生成或重复触发分析 | 同一步骤只保留一个有效任务，避免并发重复调用 | 等待当前任务完成 / 主动取消后再发起 |
| 登录状态变化 | 未登录体验后希望保存结果或跨设备继续 | 不阻断当前创作流程，但提示登录可保存资产 | 当前会话继续 / 登录后保存 |
| AI 输出不稳定 | 分析内容有偏差、生成结果偏风格或失真 | 明确提示“结果供编辑和迭代，不代表唯一正确答案” | 修改 Prompt / 调整风格强度 / 更换参考图 |
| 外部依赖不可用 | 分析模型或生图模型暂时不可用 | 若分析可用则继续展示分析结果；若生成不可用则暂停生成入口并提示稍后重试 | 先查看分析 / 稍后再生成 |

### 2.5.4 状态恢复原则

- 任一步骤失败时，优先保留用户已经完成的内容，不让用户从首页重新开始
- 分析失败时，至少保留原图和已识别出的稳定信息
- 生成失败时，至少保留当前 Prompt、参数和最近一次分析结果
- 用户重新进入页面时，应优先恢复到“最近可继续操作的稳定状态”
- 系统必须明确告诉用户：失败发生在哪一步、是否可重试、下一步建议做什么

### 2.5.5 本期明确不覆盖的用户场景

- 批量上传多张参考图并做统一分析
- 多张参考图混合风格融合
- 多人协作编辑同一份视觉配方
- 企业级审批、权限分层和品牌合规审核
- 训练专属 LoRA 或建立复杂风格资产后台

## 2.6 MVP 用户故事

### P0 用户故事

- 作为第一次访问产品的用户，我希望在首页快速看懂产品可以做什么，以便判断是否值得尝试。
- 作为想复用某种视觉风格的用户，我希望上传一张参考图，以便系统自动进行分析。
- 作为不擅长手写 Prompt 的用户，我希望系统自动分析图片并生成结构化结果，以便减少我的理解成本。
- 作为需要判断分析是否准确的用户，我希望看到结构化结果，而不是一整段文本，以便确认系统是否真的理解了图片。
- 作为想继续生图的用户，我希望系统自动生成 Prompt 和 Negative Prompt，以便我可以直接使用。
- 作为对结果有具体想法的用户，我希望编辑 Prompt 或部分分析字段，以便让结果更符合目标。
- 作为想验证风格迁移效果的用户，我希望直接生成图片，以便判断分析结果是否真正可用。
- 作为需要判断质量的用户，我希望对比参考图、分析结果和生成图，以便决定是否继续迭代。

### P1 用户故事

- 作为还没有准备参考图的用户，我希望直接使用示例图体验产品，以便快速理解能力。
- 作为希望控制贴合程度的用户，我希望通过滑杆调整风格强度，以便平衡风格一致性和生成自由度。
- 作为不想保留原图内容的用户，我希望替换主体，以便复用风格但生成新内容。
- 作为需要多轮优化的用户，我希望从当前结果继续发起下一轮生成，以便逐步逼近目标。

### P2 用户故事

- 作为长期使用产品的用户，我希望保存当前视觉配方，以便后续复用。
- 作为有不同生成需求的用户，我希望同一份视觉配方能适配不同模型，以便选择最合适的生成结果。
- 作为设计师或团队成员，我希望沉淀多个风格配方，以便形成长期可复用的风格库。

# 第三部分 UX / UE 设计

## 3.1 设计目标

UX / UE 设计需要同时满足两件事：

1. 信息足够少，用户能快速看懂
2. 路径足够清晰，用户知道下一步怎么做

因此本产品采用两页结构：

- 首页：负责讲清产品价值、建立信任、引导进入工作区
- 工作区：负责完成分析、编辑、生成、对比这条主链路

---

## 3.2 用户操作路径

用户从进入系统到完成一次生成的标准路径如下：

```text
进入首页
  -> 理解产品价值
  -> 上传参考图 / 选择示例图
  -> 跳转工作区
  -> 系统自动分析
  -> 查看结构化结果
  -> 编辑 Prompt / 调整风格强度 / 替换主体
  -> 点击生成
  -> 查看结果与对比
  -> 决定继续迭代或结束
```

这条路径的设计原则是：

- 首页不承载复杂功能
- 工作区不承载多余说明
- 每个阶段只保留当前最需要的操作

---

## 3.3 首页线框图与说明

首页的目标只有三个：

1. 讲清楚产品做什么
2. 证明它值得试
3. 让用户进入工作区

### 首页基础线框

```text
+--------------------------------------------------------------------------------------------------+
| Logo                                                                [ 登录 / 注册 ]             |
+--------------------------------------------------------------------------------------------------+
|                                                                                                  |
|                   从参考图中提炼可复用视觉语言，并生成同风格新作品                               |
|                                                                                                  |
|        上传参考图，自动分析构图、光影、色彩与风格，并输出可编辑 Prompt 与生成结果                |
|                                                                                                  |
|                   [ 上传图片 ]                         [ 试试示例图 ]                             |
|                                                                                                  |
|                   提示：不是复刻原图，而是提炼风格后再创作                                        |
|                                                                                                  |
+--------------------------------------------------------------------------------------------------+
| 能力说明：解析参考图 -> 提炼视觉配方 -> 编辑 Prompt -> 同风格生成                                |
+--------------------------------------------------------------------------------------------------+
| 示例展示： [原图]                     [分析摘要]                     [生成结果]                   |
+--------------------------------------------------------------------------------------------------+
| FAQ / 使用说明                                                                                   |
+--------------------------------------------------------------------------------------------------+
```

### 首页操作说明

- 用户先通过标题、副标题和示例理解产品价值
- 右上角提供 `登录 / 注册` 入口，用于后续账户体系承接
- 如果已有素材，点击 `上传图片`
- 如果还不确定效果，点击 `试试示例图`
- 两个入口都会把用户带入工作区

首页设计重点不是信息全面，而是让用户愿意进入下一步。

## 3.4 工作区线框图与说明

工作区是产品核心页面，用户在这里完成：

**看图 -> 看分析 -> 改内容 -> 生成图 -> 做对比**

### 工作区基础线框

```text
+--------------------------------------------------------------------------------------------------------------+
| 返回首页 | 工作区                                                                                           |
+--------------------------------------------------------------------------------------------------------------+
|                |                                                |                                               |
| 左栏：参考图    | 中栏：结构化分析结果                           | 右栏：Prompt 与生成                            |
|                |                                                |                                               |
| +------------+ | +--------------------------------------------+ | +-------------------------------------------+ |
| | 参考图预览  | | | 图像摘要                                   | | | Prompt 编辑器                            | |
| +------------+ | +--------------------------------------------+ | +-------------------------------------------+ |
| [替换图片]     | | 主体 / 场景                                 | | | Negative Prompt                          | |
| [查看大图]     | +--------------------------------------------+ | +-------------------------------------------+ |
| 图片信息       | | 构图 / 镜头 / 光影 / 色彩 / 材质            | | [风格强度滑杆]                              |
|                | +--------------------------------------------+ | [主体替换输入框]                             |
|                | | 风格标签 / 情绪氛围                         | | [模型选择] [参数设置]                       |
|                | +--------------------------------------------+ | [生成图片]                                   |
|                | | 必保留项 / 可替换项                         | |                                             |

```

### 工作区操作说明

用户进入工作区后的操作顺序应尽量固定：

1. 看左栏参考图，确认素材无误
2. 看中栏分析结果，判断系统是否理解准确
3. 在右栏编辑 Prompt 或调整主体、风格强度
4. 点击生成，等待结果返回
5. 查看右栏结果图，必要时进入对比视图继续迭代

其中：

- 左栏负责“看原图”
- 中栏负责“理解分析结果”
- 右栏负责“做决定并生成”

这样用户不需要在页面中来回找功能，操作路径是稳定的。

## 3.5 工作区关键状态

| 状态 | 页面表现 | 用户下一步 |
| --- | --- | --- |
| 分析中 | 中栏显示分析步骤进度，右栏生成按钮置灰 | 等待分析完成 |
| 分析完成 | 中栏展示结构化结果，右栏自动填充 Prompt | 判断分析是否准确并开始编辑 |
| 生成中 | 右栏显示生成进度、模型信息、耗时 | 等待结果或取消任务 |
| 生成完成 | 右栏展示结果图列表，可打开对比视图 | 对比结果并继续迭代 |
| 异常状态 | 页面显示失败原因和重试入口 | 重新分析或重新生成 |

状态设计的核心不是“展示更多反馈”，而是让用户始终知道：

- 系统现在在做什么
- 我能做什么
- 下一步该做什么

---

## 3.6 对比视图与迭代路径

结果页不能只有“生成成功”，还要支持用户判断为什么成功或失败。  
因此需要一个轻量对比视图：

```text
原图  ->  分析摘要  ->  生成结果
```

用户在这里重点看三件事：

- 风格是否接近原图
- 构图和光影是否被保留
- 当前结果是否值得继续迭代

如果不满意，用户回到工作区右栏继续：

- 修改 Prompt
- 替换主体
- 调整风格强度
- 再次生成

## 3.7 功能逻辑规则补充

### 3.7.1 核心对象定义

工作区里真正被用户操作的核心对象有三层：

- `参考图`：原始输入，不可被系统改写，只能被替换
- `结构化视觉配方`：系统从参考图中提炼出的中间层，是后续 Prompt 和生成参数的基础
- `Prompt 版本`：面向生成模型的可执行文本，可由系统生成，也可被用户手动修改

首版默认规则：

- 参考图是分析来源，不直接等于生成目标
- 结构化视觉配方是系统理解结果的主依据
- Prompt 是生成执行层，不等于唯一真实表达

### 3.7.2 输入与校验规则

- 首版只支持单张静态参考图
- 优先支持常见图片格式，如 `JPG`、`PNG`、`WebP`
- 上传完成前，不创建分析任务
- 图片无法解析、内容缺失明显或上传中断时，不进入分析阶段
- 用户未提供参考图时，不能直接发起分析或生成，但可以选择示例图进入体验

### 3.7.3 分析结果与 Prompt 同步规则

- 参考图分析完成后，系统先生成结构化视觉配方，再基于该配方生成首版 Prompt 和 Negative Prompt
- 用户编辑结构化字段时，系统应基于最新字段重新生成 Prompt 草稿
- 用户直接编辑 Prompt 时，默认只修改当前 Prompt 版本，不自动反向覆盖结构化视觉配方
- 如果用户希望用最新结构化字段重新生成 Prompt，应通过明确动作触发，避免覆盖手动修改内容
- 结构化视觉配方始终代表“系统理解层”，Prompt 版本代表“生成执行层”

### 3.7.4 必保留项与可替换项规则

- `必保留项` 主要用于描述风格迁移中建议保留的视觉特征，例如构图关系、光影气质、色彩倾向、材质语言
- `可替换项` 主要用于描述允许用户主动修改的内容，例如主体类型、局部元素、场景细节
- 当用户只替换主体时，系统默认优先保留风格、光影、材质和整体氛围
- 当用户大幅修改 Prompt 时，系统应默认提醒“当前结果可能偏离原始风格”
- 风格强度越低，系统越允许生成结果偏离原图；风格强度越高，越优先保留必保留项

### 3.7.5 生成规则

- 只有在分析完成后，生成入口才可用
- 用户可以直接使用系统生成的 Prompt，也可以在轻量编辑后发起生成
- 每次点击生成，都应记录对应的 Prompt 版本、参数和结果图
- 生成失败时，不清空当前 Prompt、参数和结构化结果
- 用户基于结果继续迭代时，默认以上一个成功版本为起点，而不是回到最初状态

### 3.7.6 状态流转规则

工作区的关键状态流转建议如下：

```text
idle
  -> uploading
  -> analyzing
  -> analysis_ready
  -> generating
  -> generation_ready

analysis_ready
  -> editing
  -> generating

generation_ready
  -> editing
  -> generating

uploading / analyzing / generating
  -> error

error
  -> retry current step
  -> previous stable state
```

规则说明：

- `editing` 是前端交互状态，不一定需要单独落库为任务状态
- `error` 不应吞掉上一个稳定状态，用户始终要能回到可继续操作的位置
- `generation_ready` 后再次编辑，不重跑分析，只更新当前 Prompt 版本和参数

### 3.7.7 权限与历史逻辑

- 首次体验默认不强制登录，优先保证体验闭环
- 未登录用户可以上传、分析、生成和查看当前结果，但不保证长期历史保存
- 登录后用户可以保存分析结果、Prompt 版本和生成记录
- 历史记录属于增强能力，不是首版闭环前置条件
- 团队协作、多人共享和复杂权限分层不纳入首版功能逻辑

---

## 3.8 UX 设计结论

本产品的 UX / UE 重点不是做复杂页面，而是把用户操作压缩成一条清晰路径：

**首页理解价值 -> 工作区看分析 -> 编辑 -> 生成 -> 对比 -> 继续迭代**

只要这条路径顺，用户就会理解：  
这不是一个“看图吐 Prompt”的工具，而是一个把参考图转成可操作视觉资产的工作台。

- 视觉模型负责看图

# 第五部分 数据指标与验证方案

## 5.1 验证目标

首版数据验证的重点，不是证明所有长期业务指标都已经成立，而是回答以下问题：

- 用户是否愿意从首页进入“参考图驱动创作”流程
- 用户是否能顺利完成“上传 / 分析 / 生成”首轮闭环
- 结构化分析结果是否真的能被用户拿来生成，而不是只被看一眼
- 用户是否能理解“不是复刻原图，而是提炼风格后再创作”的产品价值
- 当前产品形态是否值得继续扩大投入

---

## 5.2 指标体系

### 5.2.1 核心验收指标

以下指标用于判断首版闭环是否成立：

| 指标 | 定义 | 首版目标 | 说明 |
| --- | --- | --- | --- |
| 分析完成率 | 成功返回结构化分析结果的任务数 / 发起分析任务数 | `>= 95%` | 衡量分析链路稳定性 |
| 生成完成率 | 成功返回结果图的任务数 / 发起生成任务数 | `>= 95%` | 衡量生成链路稳定性 |
| 首轮闭环完成率 | 首次进入工作区后完成“分析 -> 生成 -> 查看结果”的用户数 / 首次进入工作区用户数 | `>= 35%` | 衡量首版闭环是否成立 |
| Prompt 直接采纳或轻编辑后使用率 | 使用系统初始 Prompt 或轻量编辑后即发起生成的次数 / 总生成次数 | `>= 60%` | 衡量结构化分析是否真正可用 |
| 从上传到首张结果图的中位耗时 | 从用户提交图片到拿到第一张生成结果图的中位时间 | `<= 90 秒` | 衡量首版体验时延 |
| 分析结果主观有效性 | 用户对分析结果反馈“有帮助 / 较准确”的比例 | `>= 70%` | 衡量解释层是否有价值 |

### 5.2.2 过程观察指标

以下指标用于帮助判断哪一段链路最容易流失或失效：

| 指标 | 定义 | 观察目的 |
| --- | --- | --- |
| 首页上传 CTA 点击率 | 点击上传入口的用户数 / 首页访问用户数 | 判断首页是否讲清价值 |
| 示例图体验转工作区率 | 点击示例图并进入工作区的用户数 / 点击示例图用户数 | 判断“先试试看”入口是否有效 |
| 分析后直接生成率 | 分析完成后未编辑或轻编辑即生成的用户数 / 分析完成用户数 | 判断系统分析可信度 |
| 结构化字段编辑率 | 有字段编辑行为的用户数 / 分析完成用户数 | 判断用户是否需要更高可控性 |
| 结果对比视图打开率 | 打开对比视图的用户数 / 生成完成用户数 | 判断用户是否在认真评估结果 |
| 二次迭代率 | 生成完成后继续编辑或再次生成的用户数 / 生成完成用户数 | 判断结果是否值得持续优化 |
| 登录保存意愿率 | 未登录用户在保存时选择登录的用户数 / 触发保存提示的用户数 | 判断资产沉淀能力是否成立 |

### 5.2.3 系统质量指标

以下指标用于辅助技术和运营判断上线质量：

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 上传失败率 | 上传失败次数 / 上传尝试次数 | `<= 3%` |
| 分析平均耗时 | 分析任务平均完成时间 | `<= 30 秒` |
| 生成平均耗时 | 生成任务平均完成时间 | `<= 60 秒` |
| 任务错误率 | 返回明确错误状态的任务数 / 总任务数 | `<= 5%` |
| 严重阻塞问题数 | 阻止用户完成主链路的问题数 | `0` 个可接受 |

## 5.3 埋点方案

### 5.3.1 首版最小埋点集

MVP 阶段默认只使用 **Google Analytics 4（GA4）** 做埋点与统计，不额外建设独立埋点平台。

因此首版埋点不宜过重，优先覆盖能判断“首页 -> 工作区 -> 分析 -> 生成 -> 反馈”闭环是否成立的最小事件集：

| 事件名 | 触发时机 | 关键属性 | 用途 |
| --- | --- | --- | --- |
| `page_view` | GA4 自动采集页面访问 | 页面路径 | 统计首页访问和页面浏览 |
| `workspace_entered` | 用户进入工作区 | `source_type`：上传图 / 示例图 | 判断首页到工作区转化 |
| `analysis_started` | 分析开始 | `source_type` | 统计分析起点 |
| `analysis_result` | 分析结束 | `status`、`latency_bucket` | 统计分析完成率和耗时分布 |
| `generate_clicked` | 用户点击生成 | `has_edit`、`style_intensity` | 统计生成触发条件 |
| `generation_result` | 生成结束 | `status`、`latency_bucket`、`model_name` | 统计生成完成率和耗时分布 |
| `feedback_submitted` | 用户提交主观反馈 | `feedback_type`、`rating_level` | 统计主观有效性 |

说明：

- 首页访问直接使用 GA4 自动采集的 `page_view`，不再单独自定义首页浏览事件
- `analysis_result`、`generation_result` 统一用 `status` 区分成功和失败，不拆成两套事件
- `has_edit` 用于判断用户是否在生成前编辑过内容，因此首版不单独埋 `prompt_edited`
- 二次迭代可通过同一 `session_id` 下多次 `generate_clicked` 推导，不额外单独埋点
- 深度排障不依赖 GA4，错误明细仍以服务日志和任务记录为准
- 如果后续进入增长阶段，再补充保存行为、对比视图打开率和更细粒度编辑行为

### 5.3.2 公共属性最小集

为了保证后续可分析性，首版先统一保留以下公共属性即可：

- `user_id / anonymous_id`
- `session_id`
- `source_type`：上传图 / 示例图
- `status`：success / failed（适用于结果事件）
- `latency_bucket`：如 `0-10s`、`10-30s`、`30-60s`、`60s+`

其中：

- `model_name` 只在生成结果事件中保留
- `error_code` 暂不进入 GA4 公共属性，失败排查以服务日志为准
- `prompt_version_id` 暂不作为首版公共属性，确有排障需要时再补

## 5.4 验证方式与上线节奏

### 5.4.1 首版验证方式

首版不建议一开始就做重型 A/B Test，更适合按以下节奏推进：

1. 内部走查：先验证上传、分析、生成、对比、重试、恢复等主链路是否可用
2. 定向灰度：面向少量创作者和设计师开放，观察首轮闭环和主观反馈
3. 扩大灰度：在核心指标达标后，逐步放大到更广泛的自然流量

### 5.4.2 灰度策略

- 首轮灰度优先覆盖愿意提供反馈的种子用户
- 灰度期间必须开启完整埋点和错误监控
- 如果分析完成率或生成完成率低于阈值，不继续扩大流量
- 如果主观反馈明显低于预期，优先回头修正分析质量和工作区提示，不急于扩大发布

### 5.4.3 A/B Test 使用原则

- 首版核心闭环优先做灰度验证，不强依赖 A/B Test
- 若首页转化存在疑问，可对以下内容做轻量 A/B：
  - 首页主标题文案
  - 上传入口与示例图入口的优先级
  - 示例展示样式
- 不建议首版对分析逻辑或生成逻辑做复杂 A/B，因为样本量和变量都不稳定

---

## 5.5 验收标准

### 5.5.1 首版通过标准

首版进入下一阶段的最低验收标准如下：

- 分析完成率达到 `95%` 及以上
- 生成完成率达到 `95%` 及以上
- 首轮闭环完成率达到 `35%` 及以上
- Prompt 直接采纳或轻编辑后使用率达到 `60%` 及以上
- 从上传到首张结果图的中位耗时不高于 `90 秒`
- 分析结果主观有效性达到 `70%` 及以上
- 埋点覆盖主链路关键事件，且可回溯主要失败原因
- 不存在阻断主链路的严重线上问题

### 5.5.2 暂停放量条件

若出现以下情况，首版不应继续扩大流量：

- 分析完成率低于 `95%`
- 生成完成率低于 `95%`
- 上传到首图耗时长期高于 `120 秒`
- 严重错误导致用户无法完成主链路
- 用户持续反馈“分析结果不可用”或“生成结果明显偏离参考风格”

---

## 5.6 反馈收集机制

首版除了看数据，还需要主动收集定性反馈：

- 在分析完成后，允许用户反馈“分析是否准确 / 是否有帮助”
- 在生成完成后，允许用户反馈“结果是否接近目标风格”
- 对于种子用户，补充访谈或问卷，重点询问：
  - 哪些字段最有帮助
  - 哪些结果最不可信
  - 是否真的减少了 Prompt 编写成本
  - 是否愿意再次使用或保存当前配方

# 第六部分 风险与兜底方案

## 6.1 风险清单

首版风险需要至少按以下六类统一识别：

| 风险类别 | 具体风险 | 可能表现 | 影响 |
| --- | --- | --- | --- |
| 用户理解风险 | 用户误以为产品是“复刻原图”工具 | 对结果预期过高，对偏差容忍度低 | 降低满意度，增加流失 |
| 体验风险 | 分析等待过长、结果解释不清、工作区信息过多 | 用户中途退出，不知道下一步做什么 | 降低闭环完成率 |
| 技术风险 | 上传、分析、生成链路不稳定；外部模型不可用 | 任务失败、耗时过长、结果无法返回 | 直接阻断主链路 |
| 数据风险 | 埋点丢失、任务状态不一致、结果与版本无法追溯 | 无法定位问题，也无法判断价值 | 影响验证结论可信度 |
| 合规风险 | 用户上传不具备使用权的图片，或触发敏感内容生成 | 投诉、下架、限制发布 | 影响上线安全性 |
| AI 输出风险 | 分析幻觉、风格理解偏差、生成结果失真 | 用户不信任分析结果，不愿继续生成 | 削弱产品核心差异化 |

## 6.2 首版风险应对原则

- 不把 AI 输出包装成“唯一正确答案”，而是明确为“可编辑、可迭代的建议结果”
- 任一步骤失败时，优先保留用户已完成内容，而不是让用户从头开始
- 当生成能力不可用时，尽量保留分析能力，避免整个产品完全失效
- 先灰度、后放量，用监控数据决定是否继续扩大流量
- 对外部模型、Prompt 模板和关键文案保留快速切换或关闭能力

## 6.3 降级策略

### 6.3.1 分析链路异常时

- 若上传成功但分析失败：保留原图，展示失败阶段和重试入口
- 若分析模型暂时不可用：暂停分析入口，提示稍后重试，不让用户误以为页面卡死
- 若分析结果不完整：允许返回部分稳定字段，并明确提示“结果需谨慎使用”

### 6.3.2 生成链路异常时

- 若生成失败：保留当前 Prompt、参数和最近一次分析结果，允许重试
- 若生图模型不可用：暂时关闭生成入口，但继续保留分析和编辑能力
- 若生成耗时异常：优先提示排队或处理中状态，避免用户重复提交

### 6.3.3 AI 结果质量不稳定时

- 若分析内容明显偏差：允许用户编辑结构化字段和 Prompt，而不是强制重新上传
- 若结果偏离参考风格：提示调整风格强度、替换主体或重新生成
- 若系统无法给出高可信结果：允许只展示分析结果，不强推生成

### 6.3.4 账号与历史能力异常时

- 若登录或保存链路异常：不影响当前会话内的分析和生成
- 若历史记录写入失败：优先保证当前结果可见，并提示保存未成功

## 6.4 回滚方案

首版必须支持以下回滚或紧急收缩能力：

- 通过开关关闭生成入口，只保留上传、分析和查看能力
- 回退到上一版稳定的 Prompt 模板或模型配置
- 将外部流量收缩回小流量灰度，不继续放量
- 暂停示例图之外的新上传流量，先保护已有稳定体验
- 在必要时整页展示维护状态，避免用户持续进入失败链路

## 6.5 人工介入与排障

当系统自动恢复无法解决问题时，首版需要预留人工介入能力：

- 通过 `analysis_task_id`、`generation_task_id`、`prompt_version_id` 快速定位失败链路
- 保留错误码、模型版本、耗时、关键参数，方便排障
- 对灰度用户建立反馈通道，允许集中收集“分析不准 / 结果偏差 / 页面卡住”等问题
- 当出现批量失败或明显质量回退时，优先暂停放量，再排查模型、Prompt 模板和服务链路

## 6.6 合规与内容安全底线

- 用户需要对上传的参考图具备合法使用权，本产品不承诺规避版权责任
- 对明显敏感、违规或不适合生成的内容，应保留拦截和提示能力
- 产品文案必须明确“同风格再创作”不等于“复刻原图”
- 对外展示结果时，应避免暗示系统可以 100% 忠实还原参考图

## 6.7 风险判断结论

首版风险总体可控，但前提是以下条件同时成立：

- 主链路有完整监控和埋点
- 生成能力可被快速降级或关闭
- 分析与生成任务具备可追溯标识
- 灰度放量严格依赖数据阈值，不凭主观感觉扩大发布

如果以上条件做不到，首版不应直接大规模开放。

# 第七部分 最终对齐结论

## 7.1 是否建议推进

### 结论

**建议推进。**

推进原因：

- 用户问题真实存在，且竞品已验证“参考图驱动创作”是成立需求
- 当前方案已经形成清晰差异化：不是普通图转 Prompt，而是结构化视觉配方工作台
- 首版目标明确，范围可控，具备以 MVP 方式验证的条件
- 数据指标、风险兜底和技术骨架已经能够支撑小流量验证

暂不建议的推进方式：

- 不建议一开始就做多模型平台化
- 不建议一开始就做团队协作、品牌资产后台和复杂权限体系
- 不建议在分析质量未稳定前直接大规模开放自然流量

## 7.2 本期版本范围

### V1 首版必须交付

- 首页：价值表达、上传入口、示例图入口、基础示例展示
- 工作区：参考图预览、结构化分析结果、Prompt / Negative Prompt、直接生成、结果对比
- 主链路：上传 -> 分析 -> 编辑 / 确认 -> 生成 -> 对比 -> 再次生成
- 基础数据能力：任务状态记录、Prompt 版本记录、关键埋点、错误可追溯
- 风险控制：生成失败可重试、生成入口可降级、灰度可收缩

### V1 明确不做

- 多模型深度适配
- 团队协作与复杂权限分层
- 企业级品牌资产管理
- 批量上传、多图融合、LoRA 训练
- 重型社区、模板市场和开放 API

## 7.3 进入下一阶段的前置条件

进入详细设计和开发排期前，至少满足以下条件：

- 结构化视觉配方 schema 不再频繁大改
- 首页和工作区双页流方案已被确认
- 分析与生成链路的首版模型选择已确认
- 指标、埋点、灰度和验收标准已被团队认可
- 风险方案中定义的降级和回滚口径可以被技术实现

若以上任一条件未确认，应优先补齐，不直接进入开发。

## 7.4 成功定义

首版是否算成功，不以“功能是否上线”来判断，而以“闭环是否成立”来判断。

首版成功定义：

- 用户愿意从首页进入工作区体验
- 用户能稳定完成上传、分析、生成主链路
- 结构化分析结果能够被用户直接使用或轻编辑后使用
- 用户能够理解这是“同风格再创作”而不是“复刻原图”
- 产品有证据表明值得继续投入下一阶段

首版失败定义：

- 分析或生成链路长期不稳定
- 用户普遍无法理解分析结果或不愿继续生成
- 结果质量持续偏离参考风格，且无法通过编辑改善
- 关键指标持续未达标，且灰度反馈没有改善趋势
