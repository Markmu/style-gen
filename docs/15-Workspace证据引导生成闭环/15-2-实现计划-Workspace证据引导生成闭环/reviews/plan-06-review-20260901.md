## implementer 披露专项核实

### ① preferred 验证对「详情暂不可读」（网络/5xx/401）保留会话偏好——**裁定：成立，非阻塞**

- 实现事实（`src/app/workspace/page.tsx` `handleDirectionSetPreferred` / 窗口外复验 effect / `validatePreferredDetail`）：只有 detail 返回且呈现**结构性无效事实**（不同 `analysisTaskId`、非 completed、无结果资产）才清除并展示 `direction-preferred-invalid`；GET 抛错（网络/5xx/401）一律 `return` 保留会话偏好。
- 与 plan-06 验收标准的语义边界一致性：验收标准原文「**只有详情无效才清除**」与边界场景表「preferred task failed/无资产/不同方向 → 清除 ID 并说明无效原因」均以结构性无效为清除条件——实现与两者一致。「结构性无效（detail 可读且事实无效）」vs「暂时不可读（无法得出无效结论）」的二分正是该条款的语义边界。
- 反向约束核实：plan-05 TC-5.5 在**无 detail mock** 下点击 preferred，验证 GET 命中真实 401，断言 `data-preferred-id` 保持所选项；若 401 触发清除该用例必红。本次复跑 76/76 中 TC-5.5 保持绿，证明该决策是两条契约的唯一交集。
- 与架构 §6.7.4 字面（「详情验证为无效或不可访问时才清除」）及规格 §1 字面（「无效/不可访问才清除」）存在措辞差：实现对「不可访问」取保守解释（瞬时不读 ≠ 无效，不据此销毁用户会话状态）。该解释方向与 AC-07「异常不丢创作上下文」及护栏 4 一致，且清除用户偏好属于不可逆操作、读取失败属于可重试瞬时态——保守保留是更安全的一侧。**记录为已披露的解释性偏差，不构成阻塞**；残留边界（404/403 也被当作暂不可读）见建议项 1。

### ② completeUpload → startAnalysis 窗口的恢复态陈旧 id 轮询竞态——**核实：竞态真实，修复最小且正确**

- 竞态链路核实：`handleFileSelected` 中 `ws.completeUpload` 先把 state 置 `analyzing` 但保留恢复态旧 `analysisTaskId`，随后 `startAnalysisTask` 要 `await fetch POST` 才写入新 id；窗口期内 `ws.state === "history_restored"` 轮询豁免失效，`useAnalysis(陈旧id)` 被启用，GET 命中 401 时 `useAnalysis` 内部直接 `signIn("google")`（`src/hooks/use-analysis.ts`）把用户甩向 OAuth。
- 修复核实：`restoredEntryAnalysisTaskIdRef` 仅在 `state === "history_restored"` 且有 id 时捕获一次；`holdsRestoredEntryAnalysisTask` 在 id 仍等于捕获值期间持续向 `useAnalysis` 传 `null`，新 id 写入后自动恢复轮询。与既有 `entryAnalysisTaskIdRef`（Memory 复用入口，HEAD 已有）完全对称，~12 行，不触碰其他轮询路径，无新 id 被误禁用的路径（捕获值只在恢复态观察时写入）。最小性成立。
- 残留窗口（非阻塞，见建议项 2）：ref 每挂载只捕获一次，同一挂载内第二次恢复到**不同**方向再上传时窗口重现；与既有 Memory 入口模式同构的已知边界。

## 建议项列表（均非阻塞）

1. **preferred detail 404/403 的归类**：当前所有 GET 失败（含 404/403）都按「暂不可读」保留会话偏好，且窗口外复验的 `externalPreferredVerifiedRef` 在发请求前就登记 key、失败后不再重试——指向已删除/越权 Iteration 的 preferred 会在会话内长期滞留（提示可打开详情但详情不存在）。建议后续把 404/403 视为结构性无效（清除并说明），或失败时不登记 verifiedKey 以便后续重验。
2. **披露②的二次恢复残留窗口**：`restoredEntryAnalysisTaskIdRef` 每挂载只捕获一次，同一挂载内再次恢复到不同方向后上传，`completeUpload → startAnalysis` 之间仍可能短暂轮询陈旧 id。与既有 Memory 入口模式同构；可在再次进入恢复态时重置 ref（需评估与 Memory 入口一并泛化的时机）。
3. **`IterationDetail` 类型补齐 `resultAssetId`**：`/api/generation/[id]` 已返回 `resultAssetId`（既有字段超集），但 TS 类型未声明，`validatePreferredDetail` 用 `(detail as {...})` 断言读取。建议把它加进 `src/types/models.ts` 的 `IterationDetail`，消除断言。
4. **回读协调器的潜在重复读**：`runMemoryRefreshReadBacks` 先 `invalidateQueries`（对活跃订阅已触发 refetch）再显式 `refetchQueries`/`fetchQuery`，活跃 key 可能读两次。均为读请求、不影响写幂等，仅效率层面可优化。
5. **selector 重开冷加载语义差**：迁移 query 化后，全局 staleTime 60s 内重开代表结果确认可能命中缓存（原实现每次打开冷加载）。写入后新鲜度已由协调器保证；若产品要求「每次打开必现最新」，可在 `open` 变化时显式 invalidate。
