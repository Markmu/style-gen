## 性能验收（架构 §8.1，plan-05 验收标准）

**判定：p95 = 1.7ms ≤ 300ms（预算余量约 176 倍），通过。**

### 方法说明

与 plan-04 同法（plan-04 文件"性能验收"已记录理由）：详情 API 层 `requireAuth` 需要真实 Google 会话，本地无法走 DevTools HTTP 面板；故以**真实 repository 代码路径 `findStyleMemoryDetail`**（即 `GET /api/templates/[id]` 路由内执行的 usage LATERAL 聚合 + 来源迭代/代表结果两跳联查 SQL，`src/lib/repositories/template-repository.ts:303`）直连本地 PostgreSQL（`DATABASE_URL` 取自 `.env.local`，`style_gen` 库）测量，DB 查询为接口耗时主体。

### 造数（复用 plan-04 seed SQL 方式，前缀 `PLN05B`）

一次性 seed（FK 循环列后置 UPDATE，同 plan-04）：

- 520 条 templates（≥500）：规则四元组/变量 jsonb/完整提示正文齐备，261 条 user_verified 含代表结果关联
- 561 条 assets（1 reference + 560 generated 结果资产）、1 条 analysis_tasks（任务 FK 必需）
- 560 条 generation_tasks（全部 completed + 结果资产）：t=1 来源任务；t=2..41 目标 Memory 派生 **40 条**（含 representative）；t=42..560 分挂其余 519 条 Memory
- 目标 Memory：user_verified + representative（派生之一，联查命中结果资产 URL）+ 来源迭代反向关联 + 40 条派生

测量前先断言返回数据非空且聚合正确（证明走的是聚合联查而非空结果快路径）：`verificationStatus=user_verified`、`representativeResult.imageUrl` 命中、`sourceGenerationTask.id` 命中、`usage.derivedIterationCount=40`、`lastUsedAt` 非空。
