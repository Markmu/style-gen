2. `src/components/iterations/__tests__/iteration-detail-panel.test.tsx` — 面板新增 `useQueryClient` 后 `renderPanel` 补 `QueryClientProvider` 包装属必要基建；新增 plan-05 secondaryActions 四分支断言 4 用例（可保存/已保存 + Open/来源缺失/不适用）。逐行核对：plan-03/04 既有断言（三态渲染、降级标记、纯文本安全、恢复动作、导航边界等）全部原样保留，无任何放宽或删改。

三处声明均符合全局护栏"确需越界先声明原因"的要求，理由充分。

### b. "变量按预填只读文本展示"是否偏离架构 §6.4 步骤 2 — 可接受，非偏差性 blocker

- 架构 §6.4 步骤 2 原文为"保存对话框预填：`content = promptSnapshot`、`variables = variables`（详情值）…；名称由用户必填"；§5.2 为"名称必填、内容与变量预填"。两处均只要求"预填"，未显式要求 variables 可编辑；全文中"可编辑"语义仅由"名称由用户必填"与 content 预填承载。
- 既有同类入口 `src/components/workspace/template-save-dialog.tsx`（从分析保存模板）对 variables 同样渲染为 `readOnly` 输入（"Detected Variables"预览）——只读变量预览是本产品保存对话框的既有模式，plan-05 与之保持一致。
- 该澄清已在功能文件实现规格与风险备注中先行声明（非事后追认）；red E2E 契约即按"变量默认值文本可见"（`toContainText`）订立，green 9/9 通过且无断言放宽。
- AC-06 可观察结果"保存流程以该次迭代的来源、可复用提示和变量为起点（预填正确）"满足；POST 提交体 `variables` 原样携带，下游契约无变化。
- 结论：实现与架构"预填"字面及产品既有模式一致，且已声明，判定可接受。

### c. `setQueryData` 写缓存与 plan-03 详情 hook 的 key 一致性 / 过期与串台风险 — 一致，无实质风险

- key 完全一致：面板写入 `["iteration-detail", detail.id]`（iteration-detail-panel.tsx `handleStyleMemorySaved`），plan-03 hook 读取 `queryKey: ["iteration-detail", selectedId]`（use-iteration-detail.ts）。
- 过期风险：保存入口仅存在于 completed 详情，而轮询仅在 processing 时激活（`refetchInterval` 对 completed 返回 false），`refetchOnWindowFocus: false`、`retry: false`——写入时不存在会回吐旧数据的在途请求；全局 `staleTime: 60s`（providers.tsx）内再次进入（TC-5.7）读到已保存数据，超过 staleTime 的重挂载重拉会命中服务端（POST 201 在 DB 写入完成后才返回，服务端已含 `savedTemplate`），数据最终一致。`setQueryData` 同时刷新 `dataUpdatedAt`，进一步降低误重拉窗口。
- 串台风险：回调 `useCallback` 闭包 `detail.id`，POST 在途期间切换上一条/下一条时写入仍落在原 key，不影响新选中条目；query key 含 id，天然隔离。
- 边界场景表"保存成功但详情刷新失败"以设计消除（成功回调直接消费 201，不存在可失败的二次拉取）+ TC-5.7 "POST 恰 1 次"佐证，处理方式成立。
