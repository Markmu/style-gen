## 重点复核结论（任务指令四点）

### a. `use-workspace-state.ts` 通道扩展是否破坏既有消费方 — 未破坏

- `STORAGE_VERSION` 保持 4，新增字段（`currentIterationId` / `currentTemplateId` / `previousResultUrl` / `restoredParams` / `pendingIterationRestore`）全部为可选，旧持久化条目解析路径不变（version 匹配、缺省归一为 null）。
- 300ms 防抖 `createPersistWriter` 一字未动；`flush()` 与 `writeIterationRestoreSnapshot` 共用新增的 `writePersistedStateSync`（取消挂起防抖后立即写），自动持久化行为不变（仅 effect 依赖数组追加新字段，旧流程下这些字段不变化、不产生额外写入）。
- `restoreFromPersistedState` 的改动全部由 `isIterationRestored`（仅 plan-04 恢复链路会置位）分支守卫：旧条目仍按 `analysis_ready` 挂载、`v2PromptState` 回退、来源校验清空等既有行为逐行保留（diff 逐行核对）；旧 `useHistoryRestore` 路径经 `enterHistoryRestored` 应用数据、不写 `currentIterationId`，行为不变。
- 证据：`use-workspace-state.test.tsx` 33 既有用例在 verify:fast 内全绿（98 文件/789 用例）；`workspace-ai-first-iteration-memory.spec.ts` 6/6 绿（TC-5.4 覆盖旧恢复→变化渲染全链路）。

### b. 修改 `iteration-detail-panel.test.tsx`（取代 plan-03"空占位无内置动作"断言）— 合理

- plan-03 review 报告记录的交付契约是"completed/failed 渲染空占位容器（`iteration-detail-actions`）、processing 不渲染"，plan-04 实现规格 §4 明文规定填充 completed/failed 默认主动作——该断言被计划内行为取代是定义性结果，非规避失败。

### c. "恢复态不轮询分析端点"与既有分析流程 — 无冲突

- 实现：`useAnalysis(ws.state === "history_restored" ? null : ws.analysisTaskId)`。`history_restored` 期间 query 禁用，`analysisData` 为 null，消费 effect（`if (!analysisData) return`）不动作；上传/新分析开始后状态离开恢复态，轮询按现行 task id 自然恢复（消费侧另有 `analysisData.id !== ws.analysisTaskId` 旧守卫）。
- 该状态同时被旧历史条恢复路径使用，但影响是正向收窄：恢复快照即真相，继续轮询只可能用过期分析结果覆盖恢复内容或触发 401 `signIn` 跳转；plan-04 之前轮询在恢复态本就持续活跃，本次改动未引入新竞态，只删除了有害窗口。生成轮询 `useGeneration` 不受影响（恢复条目 `generationTaskId: null`）。旧路径回归由 ai-first spec TC-5.4 绿证明。

- red 证据「未入 E2E 的分支与理由」在 red 阶段即声明该拆分，理由成立：豁免③前置要求把工作台参数构造为与目标完全一致，而参数不在 `WorkspacePersistedState` 通道（E2E 无法稳定构造）；对话框期间切换详情依赖内部时序。两者 red 用例清单本就未含，red/green 用例映射保持 1:1 无缺口。
