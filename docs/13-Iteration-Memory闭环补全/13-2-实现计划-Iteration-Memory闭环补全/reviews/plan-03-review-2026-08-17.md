## 3. 两项指定重点复核

### (a) 3 个边界场景无独立 E2E 用例的豁免（轮询 3 次失败停止、上一条/下一条跨页续切、列表 10s 重拉）

**判定：豁免可接受，非 blocker。**

依据：

1. **E2E-TDD 契约在 red 阶段即未包含这 3 项**。red 证据的用例清单 TC-3.1~3.9 由功能文件 §5 E2E 验收枚举派生（"三态详情渲染、processing 轮询序列到 completed 原地切换、failed 上下文保留、详情 5xx 保留列表可重试、上一条/下一条与返回保位"），该枚举本身不含这 3 个场景；实现方没有静默削减任何已承诺用例，red/green 9 对 9 完整闭环。task-review 维度 6 要求的是"覆盖该 feat_id 的 red + green 证据"——已满足。
2. **边界表标注透明，非隐藏式豁免**。三行均为 `done` 且说明列写明承载方式（hook `refetchInterval` 于 `fetchFailureCount >= 3` 停止、页面 `isAdvanceAfterLoadPending` effect、`use-iteration-list` `refetchInterval`），并显式注明"red 用例清单未含该场景的 E2E 用例"，符合维度 7"done 或带原因 waived"的要求。
3. **有用户可观察 UI 的部分均有自动化覆盖**：轮询失败横幅 + "Retry updates" + 内容保留由组件测试第 5 用例断言（`updatesUnavailable` + `onRetryUpdates`）；上一条/下一条边界禁用与高亮同步由 TC-3.7 + 组件测试断言（跨页续切仅是同机制的翻页延伸）；10s 重拉的"仅替换数据不重置滚动"复用与 TC-3.8 相同的 keyset 数据替换通道。
4. **纯逻辑部分经本审查代码审读确认正确**：`refetchInterval` 回调在 `retry: false` 下每个失败轮询使 `fetchFailureCount` +1，达到 3 返回 `false` 停止、成功即清零恢复节奏，与 §6.5/§8.2 语义一致；`updatesUnavailable` 要求"有数据 + processing + isError + failureCount ≥ 3"，首屏失败（无数据）仍走错误位，与规格"保留已展示内容"一致；跨页 effect 在 `hasNextPage` 耗尽或 selectedId 消失时正确复位 pending。

保留一条非阻塞建议（见 §6 第 1 条）：这三个纯逻辑路径目前没有任何层级的自动化测试（hook 级无测试文件），按 AGENTS.md 变更-验证路由（hook 变更 → 相邻 Vitest 含负向/恢复用例）与仓库先例（`src/hooks/__tests__/use-generation.test.tsx`）宜在后续补齐；不构成本次验收 blocker，因为计划文件清单与 §5 验收从未要求 hook 测试，且承载方式已在边界表如实声明。

### (b) 详情 hook 采用 React Query `refetchInterval` 而非手写轮询——是否符合 ADR-7

**判定：符合 ADR-7，且正是对"复用既有轮询模式"的正确落地。**

依据：

1. **仓库全站轮询模式就是 React Query `refetchInterval`**：`src/hooks/use-generation.ts:59` 以 `useQuery` + `refetchInterval` 轮询同一端点 `GET /api/generation/[id]`（3s，完成/失败/401 即停）；`src/hooks/use-analysis.ts:48` 同模式轮询分析任务；plan-02 的 `use-iteration-list.ts` 亦为 React Query（`useInfiniteQuery`）。ADR-7 明文"复用全站轮询模式与既有超时/失败处理，不引入推送基础设施"——新 hook 采用同库、同端点、同 `refetchInterval` 机制即是对该决策的执行；手写 `setInterval` 反而会偏离既有模式、另造一套取消与失败处理。
2. **规格三条规则全部在该习惯用法内实现**：processing 5s（§6.5.1，`ITERATION_DETAIL_POLL_INTERVAL_MS`）；观测迁移即停（§6.5.2，`refetchInterval` 回调按 `data.status` 判断）；连续失败 3 次停止 + 保留内容（§6.5.3，`fetchFailureCount` 阈值 + `updatesUnavailable`）。
3. **与既有 hook 的差异点均有规格出处**：`use-generation` 用 retry 上限（单次取的重试），本 hook 用 `retry: false` + 轮询级失败计数，对应 §6.5.3"连续失败 3 次"的语义；另增 query key 隔离与 AbortSignal（"selectedId 变化即取消在途请求"是实现规格显式要求）。

## 6. 建议项（非阻塞）

1. **hook 级负向路径无自动化测试**：`use-iteration-detail` 的 3 次失败停止/`updatesUnavailable` 置位/Retry 恢复轮询、`use-iteration-list` 的 10s 启停谓词、页面跨页续切 effect 目前无任何层级测试覆盖（组件测试只覆盖横幅 UI，见 §3(a)）。建议后续（可并入 plan-06 集成回归或单独相邻测试）补 `src/hooks/__tests__/use-iteration-detail.test.tsx`，仓库已有 `use-generation.test.tsx` 先例可循。
2. **功能文档交叉引用笔误**：功能概要"不在范围"末句写"列表含 processing 时的 10s 低频重拉在 Task 6 一并交付"，实际由 Task 7 交付且在本功能范围内（Task 6 是上一条/下一条）。仅文档内部引用不一致，行为已交付并验证，无需回改实现。
3. **游标栈记录与实际导航来源**：页面把 `nextCursor` 经 `pushCursor` 记入 store，但上一条/下一条的相邻计算实际基于 `list.items` + `list.hasNextPage`（后者同样来自末页 `nextCursor`，语义等价）。与实现规格"基于条目序列 + 游标栈"的字面有细微偏差，无可观察行为差异，建议在 plan-04/06 消费游标栈时顺手澄清。
4. **10s 列表重拉的读放大观察**：infinite query 的 `refetchInterval` 触发时按已加载页数顺序重拉全部页（深翻页 + 窗口含 processing 时每 10s N 个 GET）。仍为串行、不违反 §8.1"单会话并发 ≤ 2"的并发口径，但深翻页场景读放大会线性增长，建议在后续迭代关注（可选优化：仅重拉首页或按 processing 条目所在页重拉）。
